  **The rule of the hand-over as built (decision A).** A task run hands over as a whole at
  its end. The master of a block changes only there, in the same critical section as the
  images, so a program of another task sees a task's run whole or not at all and never a block
  half written. Within a task, a program that does not write a member takes it, when it
  begins, from the working memory of that member's writer if the writer is an earlier program
  of the same task, and from the master otherwise (`hand_in`). The first program of a task
  takes its members at `Next::Begin`, after the latch loop. When a program that is not the
  last ends, its forces are held in its working memory and the next program takes its
  members. At the last end, in `finish`, before the images are written, every program of the
  task in order holds its forces and `hand_out` copies the members it writes into the master.
  A run that faults in any program, or that a change of generation drops, hands nothing over,
  also nothing of the programs of that run that had already ended. The non-last branch takes
  the lock only if the ending program or the next one declares a block, checks the generation,
  and drops the task run if it changed. After a restart (decision B) every master is written
  whole, written members too, into the copy of every program that declares the block
  (`spread`), so a writer that counts from its own member goes on from a kept value. On an
  online change (decision C) the old process answers `Variables` as today; in the new process,
  after the existing per-program carry, `compose` rebuilds each master (each member from its
  writer's copy, a member nobody writes from the first declaring program's copy) and `spread`
  sets every copy from it. The master is `None` until the first RUN and always for a block no
  program declares, so no master is built from the zero-filled images that `Shared::new`
  makes.

  **RETAIN.** `Retained` appends, for each RETAIN block, `{path: <block>, type, bytes, layout:
  Some(<hash>)}`; the file stays a JSON array and a file of today has no `layout` key. A value
  with a layout goes to the block of that name. It is taken at a warm RUN only when its layout
  equals the block's and its bytes are exactly the block's size; otherwise the first image
  stays in the copies and in the master, never zeros. A block no program declares gives back
  its value until the first RUN and then drops it with a warning. A cold restart gives every
  block its first image. **An untaken kept RETAIN value is only a warning in the module's log
  (`tracing::warn!`), as it is today. D2 adds no way to tell the user, and nothing tells the
  user.**

  **A runtime without data blocks is unaffected.** `finish`, `hand_in` and `hand_out` return at
  once for a program that declares nothing, and the non-last branch takes no lock for one, so
  a runtime of today takes no new lock and makes no new copy. `data` is skipped when empty on
  `RuntimeProgram`, `RuntimeInstance` and `RuntimeStatus`, `layout` is skipped when `None`,
  and `Variables` reads images only and has no `data` key. What proves it:
  `a_runtime_without_data_runs_on_the_same_path` (the Retained JSON, the Variables values and
  the state's keys with and without `"data": []`), `data_has_a_fixed_shape_and_is_absent_from_a_configuration_of_today`,
  `a_retain_file_and_variables_of_today_read_and_write_back_without_a_data_key`, the existing
  `a_runtimes_file_of_today_round_trips_byte_for_byte` and
  `the_status_of_a_runtime_of_today_has_exactly_todays_keys`, left unchanged and passing. No
  byte-for-byte comparison of serialised output between `origin/dev` and this branch was run.

  - `Plan` has no `data` field of its own; `Plan.program.data` is used and `Layout.block_of`
    maps each use to its block.
  - The helper `loaded()` in `runtimes.rs` gains `data: Vec::new()` in its `RuntimeStatus`
    literal. No assertion changed.
  - R17 is the function `data_problem`, called first in `check_support`, not a branch of
    `support_problem` as the contract places it. The behaviour is the same (checked first,
    before `runs_as_today`), and the four existing tests of `support_problem` are unchanged.
  - The new assertions about a retain file and a `ProgramVariables` of today are in a new test,
    not inside `a_runtimes_file_of_today_round_trips_byte_for_byte`, so that every existing
    test passes unchanged.
  - R1 to R13 are driven through `validate` (the function a save and a load both call). Over
    HTTP only R11 and R16 are driven, and on load only R11.
  - The master is `Option<Vec<u8>>`, `None` until the first RUN (OQ1, decision D).
  - Member index `i` is the same in a program's `DataUse` and in the runtime's `DataBlock`
    because R9 requires the members to be equal in order; `Layout::new` also refuses a length
    mismatch.
  - Copies use plain slicing. They cannot leave the memory because the module refuses at load:
    R14 (a `u64` sum against `memory_size`), R5 (`u64`), R8 and R9.
  - R15: a member's own symbol `<B>.<m>`, or every symbol under `<B>.<m>.` or `<B>.<m>[`,

    characters of `0-9a-f`. R9 compares type and member names exactly; block names are matched

    not warn at every warm restart; only a host value given for it warns `<B>: the data block

    the module's answer, so the writers are named while the module is unreachable. The writer

    through R4. A program's members require `written`; a runtime block's members take none.
  - The review fixes added to the module a refusal of overlapping members in `check_data` (so

    (`Work.handed`, `check_reads`). The core does not read symbols; a save gets the first two

  **What the two reviews found, and what was done.**
  - Module review, F1 (medium, LATENT): members that overlap, and members left out of a
    block's data, were accepted, so two programs could write the same bytes and a left-out
    member was never handed over (a reproduction showed a member going backwards 10 times, and
    a member written up to 1498 whose reader's copy stayed 0). Fixed: overlap is refused in
    `check_data` and a left-out member in `check_copies`.
  - Module review, F2 (low, LIVE): after an online change the carry report counted a reader's
    copy as carried when `compose` and `spread` then set it from a new writer's first image
    (copies `[5, 5]`, `B.S.n` not listed). Fixed by `set_from_another_copy`, which moves such a
    copy from `carried` to `initialized` with a reason.
  - Module review, F3 (low, TEST-ONLY): no test covered the hold of a writer's forces in the
    non-last branch; removing that line left all 16 tests green. The code was right. A test was
    added, and a mutation removing the line turned it red.
  - Module review, F4 (low, LATENT): a second kept value for a block that exists was logged as
    `the runtime has no data block of that name`. Fixed: `unclaimed_why` says that a value was
    given before it and only the first can be taken. It is still only logged.
  - Core review, F5 (medium, LATENT): neither side checked a program's `data` against its code,
    so a program sent without the `data` its code declares read 0 for ever, and a program with
    `written: false` on a member its code assigns passed R11 beside the real writer. Fixed as
    in the last decision above. A write that leaves the value unchanged is not detected.
  - Core review, F6 (low, DOC): the MCP tool descriptions said nothing of data blocks. Fixed:
    `save_runtimes_config` and `list_runtimes` now say what `data` is, when a program needs it,
    R17, and that no route returns layout hashes, offsets or written flags.
