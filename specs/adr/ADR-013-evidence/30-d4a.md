# ADR-013 evidence: D4a

Part of [ADR-013](../ADR-013-logic-compiler-and-vm.md), section 5.

- **D4a** (the data module's workbench UI: editors for user types and data blocks, the first part
  of ADR-014's D4, 2026-11-23). A project's user types and data blocks can now be edited in the
  workbench, in a UI the data module ships. Live values of a data block, and the library editor,
  are not built.

  **Why D4 is cut in three.** ADR-014's D4 names three pieces that wait for different things.
  - **D4a** (this slice) is the editor of types and data blocks. It needs only the data module's
    routes (built in D3) and one addition to the module SDK (a refusal carries its body).
  - **D4b**, the live values of a data block per runtime, waits for C8d (the workbench's watch of
    a configured runtime and a currency rule for a runtime of several tasks) and for a change in
    the core, so that two watchers of one runtime do not replace each other's list. Doing it in D4a
    would build half of C8d inside the data UI.
  - **D4c**, the library editor (functions and function blocks), belongs to the logic module's
    UI, `frontend/packages/logic-ui`, which C8c-core was changing while D4a was built. It waits
    for that to merge.

  **The package and how the core serves it.** `frontend/packages/data-ui` is the package
  `@mythos/data-ui`, version 0.2.0, with `"mythos": {"module": "org.mythos.data", "crate":
  "plugins/data"}`. It is a Vite library build into `dist/entry.js` and `dist/data.css`. It
  imports only `@mythos/workbench-sdk` (the boundary test checks it). The shell finds a module's
  UI by the file `modules-ui/<id>/entry.js` and not by a manifest key, so the data module's
  manifest and binary serve it without a change: `scripts/e2e.sh` and
  `.github/workflows/release-assets.yml` copy `dist/entry.js` and `dist/data.css` into
  `modules-ui/org.mythos.data/`, as they do for the HMI and logic UIs. `plugins/data` and the
  package go to 0.2.0 together, as the version agreement test requires of a module and its UI; the
  entry of `mythos-data` in `Cargo.lock` is the one changed line of that file. The build of D4a
  makes no change under `crates/`, `plugins/logic` or `frontend/packages/logic-ui`.

  **The screens.**
  - **The project tree** has a section "Data" (order 30, after Programs) with two children, "User
    types" and "Data blocks", each listing what the module answered (`GET /types`, `GET /blocks`)
    in the module's order, and a row "Add new type" and "Add new data block". A row opens its
    editor on a double-click or Enter. A name that is typed into an add row and that the module
    already lists, in any case, opens the stored item. Any other name opens an editor marked NOT
    SAVED YET and writes nothing. A new item that the module does not list, whose editor was
    closed unsaved, is listed as "<name> (not saved yet)" with the unsaved mark. Under "Data
    blocks" a note is shown for each block that a configured runtime carries and that the project
    no longer has.
  - **The type editor** (kind `data-type`, title "User types", name) shows the stored Structured
    Text in a `textarea` (the same text the module gave), with Check, Save and Delete, a badge for
    the last check, a notice of what a save answered (`created`, and `changed` as answered), and a
    grid "Data blocks of this type" with each block's layout. The compiler's diagnostics are in the
    inspector's Diagnostics tab, each as `line:col message` for this type's own file, and with its
    file name or as "about the whole" for any other. A click on an own diagnostic is a button.
  - **The block editor** (kind `data-block`, title "Data blocks", name) has a select for the type
    and two radios for retain (none chosen for a new block, and Save is disabled until the type and
    one radio are chosen). It shows the saved block's layout hash, size and members (name, type,
    offset, size) as the last `GET /blocks` answered them, and a table "Configured in the
    project's runtimes": one row for each instance of the open project's runtimes configuration
    (`GET /api/v1/projects/<id>/runtimes`) whose data names the block in any case, with the type,
    layout and retain there, and the difference from the saved block named with both values.
  - **Unsaved changes** are reported with `host.setUnsaved` under the owners `data-types` and
    `data-blocks`. The module's events (`DATA_CHANGED`) are followed.

  **The rules that keep the screens truthful.**
  - A value the module did not answer reads NOT KNOWN with its reason: a block of a state that does
    not check shows layout, size and members as NOT KNOWN (`block-layout`, `block-size`,
    `block-members-unknown`), never blank or 0, and lists the module's own reasons (`state-reason`,
    file and place, or a line saying the module gave none) where it says so.
  - A read that failed is said where the list or editor would be (`tree-data-error`,
    `type-read-error`, `runtimes-error`), and no empty list, empty note or "no runtime carries it"
    is shown in its place. "no user types yet" shows only after a 200 with `[]`.
  - What is shown as saved is what the module answered. After a type save answers 200 the store
    reads `GET /types/<name>` again and shows that text as saved, since the save answer has no
    source. If that read fails, the editor says the stored text could not be read back and stays
    marked UNSAVED. After a block save or any delete the list is the answer's `blocks`.
    `changed: null` reads "Which blocks changed is not known (the project did not check before this
    save)", never "none changed".
  - A refused save shows the module's own `error` in a `notice--bad` and its diagnostics, keeps the
    draft, stays UNSAVED, and writes nothing into the saved text. A refusal that has no JSON body
    shows the status line `host.api` gave.
  - The comparison says "configured" and never "running": the heading is "Configured in the
    project's runtimes", with the note "Whether the controller runs this project and that
    configuration is not shown here." The most a row says is "laid out as saved", never "up to
    date", since an initial value in a type is outside the layout hash. A row compares nothing
    when the saved state does not check or the block list is unread, and says why.
  - A text read with `\r\n` is the same as one with `\n` for what is unsaved, since a textarea
    gives `\n`. Names go in URLs through `encodeURIComponent`. The UI has no name rule of its own:
    a name the module refuses is shown in the module's words.
  - A viewer and an operator get every editor read only (no Save, Delete or add row); Check stays.
    Without accounts anyone may edit, as in the logic UI.
  - Delete asks first with `window.confirm`, naming what follows: a program that declares the type
    or block no longer compiles, and nothing is rebuilt. The data module does not see programs.

  **The SDK addition.** `WorkbenchHost.api` throws an `ApiRefusal` (an `Error` with `status:
  number | null` and `body: unknown`, the parsed JSON or `null`). Before, only the message reached a
  module UI and the compiler's diagnostics of a refused save were lost. `ApiError` in
  `ui-shell/src/api/client.ts` has a third constructor parameter `body`, `apiRequest` sets it, and
  `host.api` throws `Object.assign(new Error(cause.message), { status, body })`. The message is the
  same as before, so every existing caller sees the same message. A 2xx answer that cannot be read
  or is not JSON is thrown as an `ApiError` with its status and a body of `null`, so it too is an
  `ApiRefusal`. The SDK contract version stays 1. A UI that is installed under a workbench that
  predates this change gets a plain `Error`: `refusalOf` then marks the refusal withheld, and both
  editors add WITHHELD ("This workbench did not hand over the module's whole answer: whether it
  gave reasons, and which, is not known here.").

  **Departures and decisions.**
  - The harness replaces one part of the real host, `events.subscribe`, with a local emitter,
    because happy-dom has no event stream. The shell's delivery of a stream event to
    `onStreamEvent` is tested in `ui-shell`'s `telemetry.test.ts`. The fake does not send
    `DATA_CHANGED` by itself: a test sends it after the write has been answered. The fake's
    type-name rule leaves out the Windows device names.
  - `plugins/data/src/tests.rs` line 1109 changed from `"0.1.0"` to `"0.2.0"`. Section 9 item 6 of
    the contract allows in `plugins/data` only the version line of `Cargo.toml` and a doc comment,
    but item 1 orders the bump to 0.2.0, and the manifest version is `env!("CARGO_PKG_VERSION")`,
    so the test that pins it fails without the change. The literal stays, so the test still pins
    the version. `lib.rs` changes in doc comment lines only.
  - `DataState.changed()` returns `{ what: 'type' | 'block'; name }` or `null` (stage 1 returned
    a name), so that a block editor can be closed too. Type behaviour is unchanged.
  - A refused block save lists the compiler's reasons inside the notice, not in the Diagnostics
    tab: a block has no text of its own and no draft check. The module's reasons why the stored
    state does not check are shown where the NOT KNOWN is explained (`StateReasons`), and no
    Diagnostics panel is set for a block editor.
  - The saved block is never copied into the block editor: it holds only what was chosen (null
    means "as saved"), and what is shown as saved comes from the module's last block list. For a
    new block, null means "not chosen", for the type as well as retain. When the editor has
    changes, the layout shown is still the saved block's, and a note says so
    (`block-layout-of-saved`): the editor never computes a layout for an unsaved choice.
  - "Add new type" opens a draft `TYPE <name> : STRUCT END_STRUCT; END_TYPE`, marked NOT SAVED YET.
    Whether the module's compiler accepts an empty `STRUCT` is NOT VERIFIED.
  - Check runs only when the button is clicked, never on open or while typing. A check of an
    earlier text is marked "(EARLIER TEXT)".
  - A 500 on `GET /types/<name>` opens the replaceable editor. A status alone cannot tell a type
    file that is not text from an unreadable `blocks.json`, so in the second case the module
    refuses the save in its own words.
  - Events of the editor's own write are matched and not taken for another's: while the write is
    unanswered an event is held, and after the answer it is matched against a count of echoes.
    An event that is not an echo and arrives while the read-back is out is followed after the
    read-back. Blocks and types keep their echoes apart ("block:" and the upper-case name).
  - An answer of a project closed since is dropped in every branch: a counter of openings, raised
    when a project is loaded or reset, is captured by each write, read-back, re-read and check.
  - The runtimes configuration is read when the project loads, each time a block editor opens and
    on a "Read again" button, since no event announces a change to it. A configuration of `null`
    (the core's answer when the project has none) is taken as no instances. The comparison uses
    the open project's saved configuration and not the status of the active project.
  - A block list read that was still out when a write was answered is dropped, so an older list
    is not drawn over the answer.
  - A draft is not dropped when its editor closes: the SDK gives a module no close notification,
    and the shell unmounts an editor on each tab switch. The tree lists the unsaved draft instead.
  - Styling: only the workbench's classes, components, icons and tokens. `data.css` holds layout
    (the grid of the two block fields, a fieldset reset, the name input of an add row) from
    `var(--gap-*)`, `var(--row-h)`, `var(--c-rule)`, `var(--c-focus)` and `var(--radius)`; its
    literals are the textarea's `min-height` of 16em and a 1px border width, as in `logic.css`.
    The add row is a plain `tree__node` with a `tree__label muted` label, so that it does not
    depend on `tree__node--action` and `tree__node--input`, which only the HMI UI's stylesheet
    defines. `logic-ui` still uses those two.
  - The Data section takes `order: 30`. How the shell sorts a section without `order` against one
    with is NOT VERIFIED.
  - The harness gives the refusal of a block named `IF` as a diagnostic about the whole, with the
    message of `tests.rs` word for word. The position the real compiler gives is NOT VERIFIED.
  - `pnpm-lock.yaml` gained only the importer `packages/data-ui`, by `pnpm install`, at the
    versions the other UIs resolve. The version bump of stage 2 changed nothing in it.

  **The two reviews and what was done.** One review took the screens and one took the package.
  Each finding was reproduced by the reviewer before it was reported.
  - Screens, LIVE: the event of the editor's own save, heard while the save's read-back was
    still out, was held and never matched, so the leftover echo swallowed the next `DATA_CHANGED`
    of somebody else's save and the clean editor kept showing the old text. Fixed in `store.ts`
    (`unanswered`, `afterReadBack`); test "this save's own event heard while its text is read back
    is matched, so a later save elsewhere is read again".
  - Screens, LIVE: the module's reasons why the stored state does not check reached no element.
    Fixed with `reasons.tsx` (`StateReasons`) under `block-not-known` and `type-blocks-not-known`;
    tests in `block-editor.test.tsx` and `type-editor.test.tsx`.
  - Screens, test only: the fake answered what the module never would (a type file that is not
    text left out of the compile, `changed: []` where the module answers `null`, a block of a type
    that does not exist laid out). Fixed in `harness.tsx`, with `fake.test.tsx`, and the R3 test
    now asserts the `changed: null` wording.
  - Screens, LIVE: a refusal or read-back failure of a previous project landed on the new
    project's editor of the same name. Fixed with the counter of openings; test "a refusal of a
    save made in a project closed since is not shown on the open project's type of the same name".
  - Screens, LIVE: "Add new type" compared names by exact case. Fixed: exact match, then any case.
  - Screens, LIVE: a new type or block whose editor was closed stayed unsaved with nothing showing
    where. Fixed by listing it in the tree, not by dropping it (see the decision above).
  - Screens, LIVE: in a new block's editor the runtimes row said "the project no longer has this
    data block" while the block list could not be read. Fixed: the row compares nothing and says
    whether the project has the block is NOT KNOWN.
  - Package, LATENT: `scripts/package-release.py` has `REQUIRED_UIS` of `org.mythos.hmi`,
    `org.mythos.discovery` and `org.mythos.logic`, and the packager's own guard lets a bundle
    through without the data module's UI. NOT FIXED: the file is outside what the slice may edit
    (the contract lists it in section 1a but not in section 6). The fix is one more id in that
    list. Today the `cp` in `release-assets.yml` fails first under `bash -e`, so the gap is in the
    packager's second layer only.
  - Package, LATENT: `host.api` threw a bare `SyntaxError` for a 2xx answer that is not JSON,
    against the SDK's declared `ApiRefusal`. Fixed in `client.ts` and `host.ts`, with the extended
    `moduleUi.test.tsx`.
  - Package, LATENT: the SDK addition had no version signal, so under an older workbench a refused
    block save showed only the summary line and nothing said reasons were withheld. Fixed on
    screen with WITHHELD; no version signal was added and `sdk` stays 1.
  - Package, LATENT: the add rows used two classes that only the HMI UI's stylesheet defines.
    Fixed in `DataTree.tsx` and `data.css`; test `styles.test.ts`.
  - Package, LATENT: the retain radios had no accessible name. Fixed with `aria-labelledby` on the
    fieldset; test "the retain choice is a group named Retain".
  - Package, test only: the test of the root scripts did not check that the package has the script
    that `pnpm` runs, and pnpm skips one without it silently. Fixed in `boundaries.test.ts`.
  - Package: the edit of `plugins/data/src/tests.rs` was reported as outside the contract. It is
    forced by the contract's own version bump, and is recorded under the departures above.

  **What was not done or not run.**

    contract's section 3 are NOT VERIFIED: a member grid and a runtimes grid with long array types
    (`.grid` cells do not wrap, so a column may push Save or the last column off screen), the type
    editor's toolbar and the block editor in a narrow work area, and the tree with 200 types or
    many "no longer has" notes.
  - `scripts/e2e.sh` and `.github/workflows/release-assets.yml` were edited and not run. They were
    checked for syntax only (`bash -n`, a YAML parse). A workflow runs only on GitHub.
  - Not covered by a test: the block path where `DATA_CHANGED` arrives while the block's own write
    is in flight, the block echo count, the dropped block list read after a write's answer, and
    the type path where the event arrives before the save's HTTP answer. The order of the stream
    event and the HTTP answer against a live controller was not observed.
  - React logs "not wrapped in act(...)" warnings to stderr from the module's own roots; the tests
    pass. Whether the logic UI's tests log the same was not compared.
  - Whether the dev autospin service links `modules-ui/org.mythos.data` is outside the repository
    and NOT VERIFIED.
  - Nothing was run on Windows or macOS by the agents. CRLF is covered by a test on Linux, and
    the names go through `encodeURIComponent`.

  **What is left out of D4a.**
  - Rename of a type or block (the module has no route, and it would change the programs' text),
    reorder of blocks (a new block is appended), per-block initial values, nested members (the
    module answers top-level members only), and where-used (the data module does not see
    programs). A program that declares a changed or deleted item breaks silently and shows at its
    next check or build in the logic module.
  - Live values of a data block (D4b, after C8d), and the library editor (D4c, in `logic-ui`).
  - No revision check on a save, so the last save wins (LATENT). A warning is shown when an event
    of another change arrives to an editor with changes, but a save can still cross an event in
    flight. A route with a precondition is a change in `plugins/data`.
  - Two watchers of one runtime replace each other's list, because the core keeps one variable
    list per instance (`crates/mythos-core/src/runtimes.rs`). LATENT in the core today, and LIVE
    once D4b exists.
