# ADR-013 evidence: C8c

Part of [ADR-013](../ADR-013-logic-compiler-and-vm.md), section 5.

- **C8c** (the logic module's runtimes and task configuration: the third slice of ADR-013
  section 2.19, 2026-11-23). The logic module stores a project's runtimes with their tasks,
  checks them, and builds a runtime of several programs into one runtime instance. The
  workbench has no editor for runtimes and tasks (C8d). Nothing is loaded by the module: the
  caller saves the instance it answers.

  **What is stored.** `<project>/logic/tasks.json`, in the logic module's own directory, so it
  travels in a device's plant slice like the rest of `logic/`. The name is not `runtimes.json`,
  which is the core's file of what is loaded. The shape, written with `serde_json::to_vec_pretty`
  and a trailing newline through `write_synced`, is:

      {
        "runtimes": [
          {
            "id": "Line1",
            "module": "vm",
            "target": "pc",
            "run": true,
            "tasks": [
              {
                "name": "fast",
                "kind": { "type": "cyclic", "interval_ms": 10, "phase_ms": 0 },
                "priority": 1,
                "programs": ["Writer"]
              },
              {
                "name": "slow",
                "kind": { "type": "cyclic", "interval_ms": 100, "phase_ms": 0 },
                "priority": 10,
                "watchdog_ms": 3000,
                "programs": ["Reader"]
              }
            ]
          }
        ]
      }

  - `TaskFile { runtimes }` and `RuntimeEntry { id, module, target, run, tasks }` have
    `deny_unknown_fields` and every key is required, with no default. `run` is a decision, and
    `tasks` must not be empty. A task is the protocol's `TaskConfig`, with its own serde:
    `priority` is required, `phase_ms` and `min_cycle_ms` default to 0 and are written back,
    and `watchdog_ms` is absent when it is not set. `tasks[].programs` holds the program names
    in the spelling of `programs.json`, whatever case a request used. A test pins the file as
    text, not only as a parsed value.
  - A missing file means no configured runtime, and no read creates it. A file that cannot be
    read or parsed makes every route that needs it answer 500 `logic/tasks.json cannot be read
    as the project's runtimes: <error>`: the four runtime routes, the program check and build,
    `POST /programs` and `DELETE /programs/:program`. It is mended by hand. `GET /programs`
    still answers. Deleting the last runtime writes `{ "runtimes": [] }`; no route removes the
    file.
  - **The target belongs to the authored runtime.** The core's `RuntimeInstance` has no target.
    The target is in `tasks.json` and decides what a program in that runtime is compiled for.
    A program's own `interval_ms`, `runtime`, `target` and `run` stay stored and editable as
    before, and a runtime build does not use them.

  **The rules T1 to T9**, checked on every write and listed again on every read. A write is
  refused for the first rule broken, in this order: T1, T2, T3, T4, T5, T6, T7a, T8, T7, T9.
  - T1 (400): the id is 1 to 64 letters, digits, `-` or `_`.
  - T2 (400): the id is not a Windows device name (CON, PRN, AUX, NUL, COM0 to COM9, LPT0 to
    LPT9), without regard to case, on every OS.
  - T3 (409): two ids do not differ only in case, since the core keeps retained values in
    `<id>.json`.
  - T4 (409): a runtime is not named like a program of the project, without regard to case. The
    reverse is refused too: `POST /programs` with the name of a runtime answers 409 and writes
    nothing.
  - T5 (400): `module` is not blank. T6 (400): `target` is a target profile. T7a (400):
    `tasks` is not empty.
  - T8 (400): every program a task names is a program of the project, without regard to case.
    It is judged before T7, so the protocol's "not a program of this runtime" never appears
    for a program the project lacks.
  - T7 (400): `check_tasks` of the module protocol, the same function the core and the VM
    runtime module use, run on stand-in programs (every program the tasks name, once each),
    with its words and the prefix `runtime '<id>': `. It is skipped when `tasks` is empty,
    because T7a says that.
  - T9 (409): a program is in at most one configured runtime.
  - On a write, T3 and T9 compare the runtime with every other one. In the list of a read they
    compare it only with the runtimes before it, so each problem is listed once.
  - Two rules on program routes: `DELETE /programs/:program` of a program a runtime names answers
    409 `program '<p>' is in task '<t>' of runtime '<id>': take it out of the runtime first`,
    and nothing is changed. `POST /programs` refuses a Windows device name (the words of T2, for
    a program), for a new program only: a program already so named still reads, checks, builds,
    lists and deletes. This is contract section 10 item 3.

  **The six routes, each an MCP tool of its own**, declared in the module's manifest after the
  library's, in this order. Every summary says that nothing is loaded. The MCP argument for
  `:runtime` is `runtime_id`.
  - `GET /runtimes`, viewer, `list_logic_runtimes`: `{runtimes, implied, problems}`. `implied`
    is each program no task names, as a runtime of its own with the program's name as its id,
    its module, target and run, and the task the core derives for it. `problems` is the rules
    the stored file breaks, empty for a file written through the routes.
  - `GET /runtimes/:runtime`, viewer, `get_logic_runtime`: `{runtime, implied}`, 404 for an id
    that is neither configured nor implied.
  - `PUT /runtimes/:runtime`, engineer, `save_logic_runtime`, body `{module, target, run,
    tasks}`, all required, no other key: `{runtime, created}`. The event
    `LOGIC_RUNTIMES_CHANGED` follows, `{project, runtime, what: saved}`.
  - `DELETE /runtimes/:runtime`, engineer, `delete_logic_runtime`: `{deleted: "<id>"}`, the
    stored spelling, with the event `what: deleted`. 404 for an id that is not configured, an
    implied one included. It reads `tasks.json` only. It deletes by the exact id, then by an id
    that differs only in case.
  - `POST /runtimes/:runtime/check`, viewer, `check_logic_runtime`, an optional draft body that
    is the whole save body and is never saved.
  - `POST /runtimes/:runtime/build`, engineer, `build_logic_runtime`, no body, needs `tags`.
  - A `PUT` replaces the runtime with exactly that id. Another spelling of a stored id is added
    and then refused by T3. `GET` of one finds configured runtimes before implied ones.
  - The event is not `LOGIC_PROGRAMS_CHANGED`, whose `created` and `deleted` the workbench acts
    on to reload its list.
  - The module's writes hold an operating-system lock (`std::fs::File::lock`) on
    `logic/.lock.tmp`, as the data module's do, besides the in-process mutex. A read takes no
    lock: a read is a `GET`, or a `POST` ending in `/check` or `/build`. `programs.json` and the
    program sources are written through `write_synced` (pid-named temporary, `create_new`,
    `sync_all`, rename) in place of the fixed `programs.tmp`. This closes the note of D3 that two
    processes during a hot swap can lose a write, for the rules above, which span two files.
    `Logic::serve` does the parameter check, the mutex and the lock and returns the reply and
    the event; `Service::handle` sends it. What is on the wire is unchanged.

  **What a runtime build does and answers.** For a configured runtime, `POST
  /runtimes/<id>/build` refuses with the first rule broken (its status), then, for each
  program in task order, checks the entry with the runtime's target, compiles it for that
  target from one snapshot of the project, and checks its bindings. It takes the union of the
  programs' data blocks, deduplicated without case, with `retain` from `blocks.json`, and
  refuses what the core would refuse, with the prefix `runtime '<id>': `: `check_tasks`,
  `check_data`, an output tag bound by two programs, a published tag published by two, and an
  event task whose tag no program reads, as a value, into a BOOL. The answer, 200, is:
  - `{version, warnings, programs: [{name, version, code_size, memory_size}], replaces,
    instance}`, and `project_problems` when the stored data does not check.
  - `instance` is `{id, module, run, program | programs, tasks, data?}`: one program in
    `program`, several in `programs`, `tasks` always, `data` only when not empty. There is no
    target in it. The tasks and the instance's program names are the compiled PROGRAM names.
    `programs[].name` of the answer is the project's name for the program.
  - **`replaces`** is the ids the programs run under alone, which are their names. The caller
    removes those instances from the core's when it saves `instance`: the core refuses a block
    in two runtimes (R16) and an output with two writers otherwise.
  - **The versions.** A program's version in a runtime is a hash of its bytecode, the task it is
    in as configured in `tasks.json`, its bindings, and its data layouts. The program's
    unused `interval_ms` is not in it. A task change (kind, priority, watchdog, members, order)
    changes the versions of that task's programs. The runtime's `version` is its programs'
    versions joined with `, ` in instance order, which is what the core reports as a runtime's
    version. It does not change with `run` or `retain`.
  - **The RETAIN warning.** For each program with a RETAIN variable, `warnings` says that RETAIN
    values are kept per runtime id, not per program: a warm load of the runtime puts into each
    RETAIN variable the value kept under that runtime id for a variable of the same name, type
    and size, whichever program ran in it before, and none of the values kept while the
    program ran alone as its own runtime; a cold load starts every RETAIN variable from its
    initial value. The warning of unregistered tags is given too, prefixed by the program.
  - **The module loads nothing.** It cannot call the core (ADR-011). The caller saves
    `instance` with `PUT /api/v1/projects/<id>/runtimes`, removing the ids in `replaces`.
    The build answers only what is in the saved files.
  - An implied id gives, byte for byte, the answer of `POST /programs/<id>/build`. A check of an
    implied id gives `{ok, runtime, version?, programs: [the program's check answer plus name],
    problems: []}`.
  - `POST /runtimes/<id>/check` of a configured runtime gives `{ok, runtime, version? (only
    when ok), programs: [{name, ok, diagnostics, binding_problems, version?, code_size?,
    memory_size?}], problems, data?, project_problems?}`. It does not refuse for a compile
    error: it lists it. A draft body is the whole save body, put in as `PUT` puts it and checked
    against the stored rest with T1 to T9. A body that is absent, `null` or `{}` means the
    stored runtime, and a partial body is 400.
  - A runtime of several programs refuses a program whose source declares a PROGRAM named
    otherwise than its entry (case aside), because its variables are named
    `<program>.<variable>` there. A runtime of one program accepts it.

  **A project of today is unaffected.** With no `logic/tasks.json` every route answers as on

  **What changed for a program in a configured runtime.**
  - Its build, `POST /programs/<p>/build`, answers 409 `{error: "program '<p>' is in task '<t>'
    of runtime '<id>': build that runtime with build_logic_runtime", runtime}`. When the
    runtime's id is not a valid id (a hand edit), the 409 says the runtime cannot be built, why,
    and to take it out with `delete_logic_runtime`. Once the runtime is deleted the program builds
    alone again.
  - Its check, `POST /programs/<p>/check`, has today's keys. It compiles for the runtime's target
    and its `version` is the version in the runtime, equal to the runtime build's
    `programs[i].version`. A program of `rp2040` is checked ok in a `pc` runtime.
  - The `build_logic_program` summary no longer says to compose by hand the instance of
    programs that share a block. It says a program of a configured runtime is built with
    `build_logic_runtime`.
  - The workbench (`frontend/packages/logic-ui/src/programs.ts`, `ProgramEditor.tsx`): the editor
    reads `GET /runtimes` into the runtimes view. `runState` gives UNKNOWN, with the runtime and
    the reason, for a program a configured runtime runs, in place of NOT LOADED. The reason reads
    `program <p> runs in runtime <id>, which this editor does not show yet` (with the words
    `with other programs` when there are several). When that runtime is not loaded it reads
    `... is in runtime <id>, which is not loaded and which this editor does not show yet`, and
    adds that its build alone, loaded before, still runs when it does. Load, Load cold and the
    Runtime card's Run, Stop, Unload and Release are disabled with that reason as their title,
    and the store sends no request for download, unload, command, force or release of such a
    program. While the configuration cannot be read, a program that no runtime of its own name
    runs is UNKNOWN with the read error. A program not in a configured runtime is read as on
    `origin/dev`: only the runtime named like it.

  **Departures from the contract and decisions.**
  - `Logic::handle_in` returns its events instead of sending them. A new `Logic::serve`, as the
    data module's `Data::serve`, does the checks and the locks and returns the reply and the
    event, and `Service::handle` sends it, because `mythos_module::Events` has no public
    constructor and a unit test could neither pin an event nor run two `Logic` values against
    one directory. `tokio` (features `macros`, `rt`) is a dev-dependency of `plugins/logic` for
    it, as in `plugins/data`.
  - The stage 1 agent ran `git merge --ff-only origin/dev` where the brief said rebase, because
    the branch had no commit of its own; it is the same result. The stage 2 agent ran
    `git rebase --autostash origin/dev`, which rewrote stage 1's commit from `1843337` to
    `d0e4f0e`.
  - A program's version in a runtime hashes the task as configured in `tasks.json` (the stored
    program spellings), not the `TaskConfig` written into the instance (the compiled PROGRAM
    names) as the contract's step 4 says. The two differ only in the case of a program name. It
    lets the program check give the runtime's version without compiling the task's other
    programs. Build and check use one function and a test shows their versions equal.
  - The runtime's version is the programs' versions joined with `, `, not a hash over module,
    target, tasks, programs and layouts as the contract's step 8 says (review finding 8). A change
    of the module alone no longer changes it, as with the core's version line.
  - Vitest was run from `frontend/`, not from `frontend/packages/logic-ui`: in the package every
    test fails with `act is not a function`, an untouched file included, because the vitest
    configuration is only at `frontend/`.
  - The Load buttons are in the editor toolbar (`ProgramEditor.tsx`), not the Runtime card.
    Both now carry the reason as their title, and the store refuses the five commands itself.
  - `check_alone` (the check of an implied id) copies `project_problems` to the top level and
    leaves it in `programs[0]`; the contract says only the program's answer under `programs[0]`.
  - The stage 1 manifest test was extended to the six routes. The only changed existing
    assertion outside it is the tool list above.
  - Decisions: a stand-in program for a program the project lacks gets interval 0, which
    `check_tasks` does not read and nothing answers; an implied runtime is every program not
    named in any task of any configured runtime, a runtime with problems included, in
    `programs.json` order; the output and published-tag owner is `<id>/<program>` with several
    programs and `<id>` with one, as the core's; the event-task rule is the VM's, a BOOL symbol
    matched without case; the RETAIN warning is given for a program with any RETAIN symbol; the
    module version is 0.7.0 for the whole slice, and `logic-ui/package.json` is 0.7.0 so the
    version-agreement tests of the core hold (3 passed).
  - `GET /runtimes` and `GET /runtimes/:runtime` compile each implied program alone to give the
