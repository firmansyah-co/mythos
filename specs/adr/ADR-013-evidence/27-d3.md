# ADR-013 evidence: D3

Part of [ADR-013](../ADR-013-logic-compiler-and-vm.md), section 5.

- **D3** (the data module, and the logic module building with a project's types, data blocks and
  library: the third slice of ADR-014, 2026-11-22). A type and a data block made in the data
  module can now be used by a program that the logic module builds. The editor is not built
  (D4), and the logic module still builds one runtime instance per program (C8c).

  **The data module** (`plugins/data`, package `mythos-data` 0.1.0, binary
  `mythos-module-data`, id `org.mythos.data`, provides `data`). It owns a project's user types
  and data blocks and is the only writer of them on disk, in `<project>/data/`:
  - `types/<Name>.st`: one `TYPE ... END_TYPE` declaring `<Name>` and nothing else.
  - `blocks.json`: the data blocks, in declaration order (a new block is appended, a replaced
    one keeps its place). `blocks_file_text` writes exactly this shape, one block per line,
    two spaces and four spaces of indent, a trailing newline, and `{ "blocks": [] }` over
    three lines when there is none:

        {
          "blocks": [
            { "name": "Recipe", "type": "RecipeData", "retain": false },
            { "name": "Line", "type": "LineState", "retain": true }
          ]
        }

    Reading goes through serde into `BlocksFile { blocks }` and `BlockEntry { name, type,
    retain }`, both with `deny_unknown_fields`, and `retain` has no default, so a file with an
    unknown key or without `retain` is refused (S14) and not cut. There is no per-block
    initial value and no "writable from outside".
  - Every write is checked first with `check_project` over the whole new state, and is refused
    if that state does not check, so the files on disk check unless they were edited by hand.
    A write changes exactly one file.
  - The file rule, which the logic module repeats word for word: a regular file directly in
    `types/` (a link or a directory is ignored), named `<stem>.st` with exactly the lowercase
    extension, whose stem is a type name. A name that is not UTF-8 is ignored. Types are
    sorted by stem in byte order. Anything else in the directory (`X.tmp`, `notes.txt`,
    `Bad-Name.st`, `Y.ST`) is ignored.
  - A type name is an ASCII letter or `_`, then ASCII letters, digits or `_`, no `__`, not
    ending in `_`, at most 64 characters, and never a Windows device name (CON, PRN, AUX, NUL,
    COM0 to COM9, LPT0 to LPT9, compared without regard to case on every OS). Names that differ
    only in case are one name: a write under another spelling is refused (S2, S9), a read or a
    delete finds the stored spelling and answers with it, and a delete removes the path built
    from the listed stem, never from the request. When both an exact spelling and another
    one are stored, the exact one is taken first.
  - Eight routes under `/api/v1/projects/<id>/data/`, each an MCP tool declared in the
    manifest, each summary saying that nothing is built or loaded: `GET /types`
    (`list_data_types`), `GET /types/:type` (`get_data_type`), `PUT /types/:type`
    (`save_data_type`, body `{source}`), `DELETE /types/:type` (`delete_data_type`),
    `GET /blocks` (`list_data_blocks`), `PUT /blocks/:block` (`save_data_block`, body
    `{type, retain}`, both required), `DELETE /blocks/:block` (`delete_data_block`) and
    `POST /check` (`check_data`, body `{type?, source?}`, both or neither). Reads need the
    viewer role and writes the engineer role. A route's MCP argument for `:type` is `type_id`.
  - A block in an answer, when the state checks, has `name`, `type`, `retain`, `layout` (16
    hex digits, the compiler's), `size` and `members` (`name`, `type`, `offset`, `size`).
    When the stored state does not check, a block has only `name`, `type` and `retain`: no
    layout, size or members, never a zero. `PUT /types` and `PUT /blocks` answer `created` and
    `changed`, the names of the blocks whose layout differs from before the write, new blocks
    included, and `null` when the state before did not check. This is how a caller sees that a
    type change makes programs out of date. A save, a delete and a check also answer `blocks`.
  - After each write the module sends the event `DATA_CHANGED` with `{project, what: type |
    block, name, change: saved | deleted}`.
  - A type's source must declare the one type named in the path and nothing else (S4); this
    is judged after the compiler's own diagnostics, which win. A type that a block uses, or
    that another type uses, cannot be deleted (S5, S6).

  **The logic module** (`plugins/logic`, version 0.6.0; `frontend/packages/logic-ui`
  `package.json` has the same `"version"`, and nothing else under `frontend/` changed):
  - **A library**, `<project>/logic/library/<Name>.st`, of functions and function blocks. A
    PROGRAM in it is refused, and so is a TYPE (L3), because the data module is the one owner of
    types; a TYPE in a program's own source stays allowed as today. Five routes, each an MCP
    tool, appended to the manifest after `build_logic_program`: `GET /library`
    (`list_logic_library`), `GET /library/:name` (`get_logic_library_source`),
    `PUT /library/:name` (`save_logic_library_source`, body `{source}`, create or replace, not
    compiled), `DELETE /library/:name` (`delete_logic_library_source`) and `POST /library/check`
    (`check_logic_library`, body `{name?, source?}`, both or neither). A library source's name
    follows the library name rule and the same case and device-name rules. A save sends
    `LOGIC_LIBRARY_CHANGED` with `{project, name, what}`. The file rule is the data module's.
  - **Building with the data.** Before every check and build the module reads
    `Path::new(data_dir).parent().join("data")`: `types/`, `blocks.json` and the library. It
    never writes there. If `data_dir` has no parent the answer is 500 naming the path; a
    missing `data/`, `types/`, `blocks.json` or `library/` means empty, and a read creates no
    directory. A program is compiled with the data module's types followed by the library
    sources, and with the blocks.
  - **What a build answers.** The instance gains `data` (the protocol's `DataBlock`, with
    `retain` taken from the block of that name in `blocks.json`), only when it is not empty;
    `instance.program.data` is the compiler's `Compiled.data` mapped field by field. `check_data`
    from the protocol runs on the built instance, and what it refuses (R3, R12 and the others)
    is a 400 `{error: <its message>}` (L5) and not a build; in a check its message is added to
    `binding_problems`. A check answers `data` when the program declares blocks, and
    `project_problems` when the stored data does not check. A build's `version` also hashes
    `Compiled.data` only when it is not empty, so a layout change changes the version, and a
    toggled `retain` changes `instance.data` but not the version. The `build_logic_program`
    summary says that a data block in two runtimes is refused when saved, and that programs
    sharing a block go in one instance's programs.
  - **Data that does not check.** The stored data is checked by itself first. If it does not
    (a block of a missing type, a `blocks.json` that cannot be read, a type file that is not
    text), the program is compiled without the blocks and `project_problems` says why, so a
    program without `VAR_EXTERNAL` builds to the bytes and the version it had, and one with
    `VAR_EXTERNAL` fails with the compiler's `there is no data block ... in the project`. When
    only the blocks do not check and the types do, the types are still given to the library.
  - Diagnostics from the project's other files carry `source`: `data/types/X.st` or
    `logic/library/X.st`. The program's own diagnostic gets a `source` (`Tank.st`) only when
    the project has a library or types.

  **The two modules meet only in the project's files.** Neither calls the other and neither
  depends on the other in `[dependencies]`. A program builds with the data module unloaded
  (tested). The logic module's reading of `<project>/data/` is the exception to ADR-011
  section 2.2 that the decision adds there, and ADR-014 section 2.8 names it. There is no
  protocol change and no core change.

  **A project of today is unaffected.** With no `data/` and no library, the module takes the
  two `Sources` literals it had, `data` and `project_problems` are absent from every answer,
  and the instance, `program` and check keys are today's. What proves it: the unit test
  `a_project_of_today_checks_and_builds_with_exactly_todays_keys` pins the versions of the
  four plant programs as literals read from the tree before `version_of` changed (TANK
  `d3adaba64d45`, LD `603a39003bec`, FBD `018750a43b66`, SFC `a1226c2936b9`); before the
  change, the check and build JSON of the four was saved, and after it, with an empty
  `data/types`, it compared identical (8 lines); the four plant tests of `logic_module.rs` and
  `a_runtimes_file_of_today_round_trips_byte_for_byte` ran unchanged and green; and
  `a_project_of_today_answers_without_any_data_key` checks it through the server. A program
  without `VAR_EXTERNAL` builds the same bytes and version beside types, blocks and a
  library. The data module for a project of today answers empty lists and creates no file on
  a read.

  **Departures from the contract and decisions.**
  - `blocks.json` is written by a hand-written formatter, not `serde_json::to_vec_pretty`, because
    the contract's literal (one block per line) cannot be produced by it. The literal is
    pinned byte for byte. Values go through `serde_json::Value`, so they are escaped.
  - The data module's unit tests call `Data::serve(&HttpCall)`, which returns the reply and the
    event data, because `mythos_module::Events` has no public constructor; `Service::handle`
    is `serve` followed by sending the event. The logic module's library routes are
    split the same way (`library`).
  - `README.md` was edited by the implementer of stage 1 (the one `cargo build` line), which
    the brief for that stage did not allow; the contract names it in its list.
  - D1 `GET /types` and D2 `GET /types/:type` also read `blocks.json`, so an unreadable
    `blocks.json` makes S14 come from every route, listing types included.
  - Reads and deletes find a name without regard to case; writes refuse another spelling.
  - A block delete whose resulting state does not check (possible only after a hand edit) is
    refused with 400 and a message of the S6 form that names the block. A state with two
    independent hand faults needs a hand edit to repair, for type saves, type deletes and
    block deletes alike; an unreadable `blocks.json` refuses every route (S14). This is the
    decision OQ3 (a write that leaves the state not checking is refused), not a defect.
  - S5 is judged before the check, S4 after it. A draft that checks but breaks S4 answers 200
    with `ok` false and no layout. Only `PUT /blocks` has `additionalProperties: false`; the
    other bodies accept extra keys, as the logic module's do.
  - The data module's temporary is `.<file>.<pid>.tmp`; it is removed if left, created with
    `create_new`, written, `sync_all`ed and renamed. The logic module has its own copy of that
    helper, since the modules may not share code; `programs.json` still uses the old
    `write_atomic`.
  - **A lock the contract did not ask for.** Contract OQ13 accepted that two processes during a
    hot swap can lose a write. The data review showed that more can happen: one process deletes
    `types/T.st` while the other saves a block of `T`, each passes its own check, and
    `blocks.json` then names a type that does not exist. So every write route of the data
    module holds an operating-system lock (`std::fs::File::lock`) on `<project>/data/.lock.tmp`
    while it reads, checks and writes, besides the in-process mutex; reads take none. This adds
    one persistent file, `data/.lock.tmp`, made by the first write and never removed (removing it
    would let two writers lock different files); it ends in `.tmp`, so the plant slice leaves it
    out. `File::lock` is stable since Rust 1.89. The fixer declared that in the data
    module's own `Cargo.toml` against the workspace's 1.82; since the workspace cannot be built
    without its member, the orchestrator raised the workspace's `rust-version` to 1.89.0 and
    the README, `docs/guides/getting-started.md` and the two architecture documents that quote
    it say 1.89. The logic module reads without the lock, so its
    snapshot is not closed. The wait on the lock is NOT MEASURED.
  - The logic module has `mythos-data` as a dev-dependency, used only by the test that
    compares the two copies of the file rule; `module_boundaries.rs` does not count
    dev-dependencies and passes.
  - The existing unit tests of the logic module call `check` and `build` through two local
    wrappers that pass an empty project; no assertion changed.
  - Library file rule: the type file rule, with the stem passing the library name rule.
    A library file that is not text refuses every program as any library mistake does, and its
    own routes can replace or delete it. `logic/library` being a file is still a 500 naming the
    path, since the library is the module's own directory and no route can repair it.
  - `instance_data` finds `retain` by the project's spelling without regard to case; if no
    entry matches it answers 500 and a check reports it, with no default made up.
  - `project_problems` is in the 200 build and in the 400 after compiling; the refusals that
    come before compiling (entry, target) have none.
  - The first commit of stage 2 was refused by the pre-commit hook because dev had moved (CI
    files only); the branch was rebased onto `origin/dev`.
  - `pnpm-lock.yaml` records no version for `packages/logic-ui`, so only `package.json` changed.
    `pnpm install --frozen-lockfile` was not run.

  **What the two reviews found, and what was done.**
  - Data module, medium, LATENT: two processes during a swap could leave files that do not
    check (a block naming a deleted type; 198 of 200 rounds in the reproduction). Fixed with the
    lock above; the same reproduction then gave 0 of 200 and the race tests pass. A real
    two-process hot swap was not run; the test models two processes with two `Data` values.
  - Data module, medium, LATENT: a type file that is not UTF-8 made every route answer 500,
    repair routes included, and the logic module's `read_project` failed the same way. Fixed:
    such a file is listed and does not check (a diagnostic naming it); its own PUT and DELETE
    repair it; the logic module reports it in `project_problems`.
  - Data module, low, LATENT: the temporary was opened with `File::create`, which follows a
    link, so a save wrote outside `data/` and renamed the link over the type file. Fixed with
    remove-then-`create_new`.
  - Data module, low, LATENT: with two hand-made spellings on a case-sensitive file system, an
    exact request reached the other file. Fixed: the exact spelling is found first, in both
    modules.
  - Data module, low, DOC: a state with two independent hand faults cannot be mended by routes.
    No change; it is the decision stated above.
  - Data module, low, TEST-ONLY: no test made concurrent calls, put a link in `types/`, or
    pinned the pid in the temporary's name. Tests added (listed above).
  - Logic module, medium, LATENT: when the data did not check, the types were left out as well
    as the blocks, so a library source using a type refused every program, against the rule
    that a program is never refused for data it does not use. Fixed: the readable types are
    checked alone and, if they check, still given to the library.
  - Logic module, medium, LIVE: one library file that is not UTF-8 made every library route
    and every program's check and build answer 500, repair routes included. Fixed: names come
    from the directory only, and such a file refuses programs as a library mistake with its own
    routes able to replace or delete it.
  - Logic module, low, LATENT: other broken shapes (`blocks.json` a directory, `data/types` a
    file) made every program's check and build answer 500. Fixed: they are `project_problems`.
    A file removed between listing and reading is skipped in both modules; that case was not

  **Two programs sharing a block.** The logic module builds one runtime instance per program,
  and the core refuses a block that is in two runtimes (R16). Two programs that share a block
  can therefore be loaded only as one runtime composed by hand, with `programs` and `tasks`,
  until the logic module builds runtimes of several programs (C8c). Loading them one by one is
  refused at the second with R16's text.

  **Two processes during a hot swap.** The data module's writes are locked between processes,
  so they cannot leave files that do not check. The logic module's library writes and its
  `programs.json` writes are not: two processes during a hot swap can lose one of two
  simultaneous writes, as the logic and HMI modules can today. This is NOT TESTED.

  runtime slices.
