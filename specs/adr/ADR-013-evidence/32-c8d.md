# ADR-013 evidence: C8d-1

Part of [ADR-013](../ADR-013-logic-compiler-and-vm.md), section 5.

- **C8d-1** (the runtimes and tasks editor in the logic module's workbench UI, with Build and Load
  of a configured runtime, the first part of section 2.19's C8d, 2026-11-23). A project's
  configured runtimes and their tasks can now be listed, edited, checked, saved and deleted in the
  workbench, and a configured runtime can be built and loaded from it. No route, no MCP tool and
  no Rust behaviour changed: the six runtime routes of the logic module and the core's runtimes
  routes existed since C8c, and the one Rust edit is the version line of `plugins/logic`. The
  state of a task, the watch and the force of a program in a configured runtime, and their live
  views are not built.

  **Why C8d is cut in two.** C8d-1 is the part that needs no change outside the logic module's
  UI, one shell file for the HMI tag list and a type: it edits and loads the configuration. C8d-2
  shows what a task does (state per task, the program editor's live views, watch and force of a
  program that a configured runtime runs, Settings → Runtimes with its tasks). C8d-2 waits for
  the core's watch lists. The core keeps one watch list per runtime instance, so two watchers of
  one runtime replace each other's list; C8d-2 would make that common, since two programs of one
  runtime share one runtime id. That change to the core is a slice of its own, before C8d-2 and
  before ADR-014's D4b. C8d-1 adds no watcher: the runtime card reads the `GET /api/v1/runtimes`
  poll that the program editor already uses and never calls the watch route.

  **What the slice adds.** All of it is in `frontend/packages/logic-ui`, version 0.10.0, with
  `plugins/logic` at 0.10.0 (the version agreement test requires a module and its UI to match),
  and two files of the shell for the HMI tag list.
  - **The tree section.** "Runtimes" (id `logic-runtimes`, order 22, between Programs 20 and
    Library 25) lists what `GET /runtimes` answered, in the module's order, each with the
    icon Cpu. A runtime opens the editor kind `logic-runtime` (title "Runtimes", the id). A
    program that runs alone (`implied`) is not listed. A failed list read shows the module's
    words (`tree-runtimes-error`) and lists nothing. "No runtime is configured: every program runs
    alone." shows only after a 200 with `runtimes: []`, and "Reading the runtimes" before. A
    non-empty `problems` puts a count on the node, with each problem in its title. An engineer
    gets the row "Add new runtime" once the list is read. An id that the list holds in any ASCII
    case opens the stored runtime. Any other id opens an editor marked NOT SAVED YET and writes nothing. The
    UI has no id rule: the module's check of the draft answers T1 to T4 in its own words. A
    runtime with changes here that the module does not list (new, or deleted elsewhere) is listed
    apart with the unsaved mark and the reason ("not saved yet", "deleted elsewhere; changes here
    not saved" or "changes here not saved"), so its draft can be reopened.
  - **The editor and its form.** Opening reads `GET /runtimes/<id>` (the id through
    `encodeURIComponent`). A 404 shows the module's words and no form. An implied id is said to be
    a program running alone and has no form. The form has the module (a select of the installed
    modules, read once from `GET /api/v1/runtimes` when the editor opens, with the stored one
    marked "(not installed)" when absent; free text with the reason when the modules could not be
    read), the target (free text: no route lists target profiles, T6 refuses a wrong one), the
    run choice (two radios, neither chosen for a new runtime) and the tasks. A task has a name, a
    kind (cycle, cyclic, startup, event; none chosen for a new task), the fields of its kind
    (shortest cycle; interval and phase; tag), a priority (empty for a new task), a watchdog
    (empty is the module's default, which the form says) and its programs in order, with up, down
    and remove, and an "Add program" select of the project's programs. A program that another
    configured runtime holds is offered disabled with "in runtime <id>"; when that list could not
    be read the hint says it is not known and no program is disabled on a guess. Tasks move up and
    down. The kinds the selected module's `profile.tasks.kinds` lacks are marked, and a module
    that declares none is said not to say that it runs tasks.
  - **Check.** `POST /runtimes/<id>/check` with the whole draft, numbered; an older answer is
    dropped. The badge reads NOT CHECKED, CHECKING, CHECKS or DOES NOT CHECK, with EARLIER DRAFT
    once the draft changed. The inspector's Diagnostics tab (owner `logic-runtime-check`) lists
    the module's `problems`, then per program its diagnostics (each opens that program) and
    binding problems, and `project_problems` apart; its count is problems plus every program's
    diagnostics and binding problems, null before a check and after a refused check. A draft that
    is not a complete body (no run choice, a task without a kind or a priority, a cyclic task
    without an interval, a number that is not a finite number) is not sent: the form names the
    missing field, Check and Save are disabled and the store sends nothing.
  - **Save.** `PUT /runtimes/<id>` with the four keys the module takes (module, target, run,
    tasks; the id is in the address), then `GET /runtimes/<id>` again. What is shown as saved is
    the answer of that read, with the program names respelled by the module. When the read after
    a 200 fails, the editor shows the `runtime` the PUT answered and says the read failed.
    Save does not check first. A refusal keeps the draft and shows the module's `error`
    verbatim. The note "Nothing was built or loaded." follows a save.
  - **Delete.** It asks `deleteRuntimeQuestion(id)` first (a configured runtime that the
    controller runs goes on running until it is unloaded). A cancel sends nothing. A 200 closes
    the editor and reads the list again. A refusal shows the module's words.
  - **Unsaved, events, viewers.** The editor is UNSAVED when the canonical body of the draft
    differs from the stored one; the tree and the workbench's unsaved owner `logic-runtimes`
    follow. `LOGIC_RUNTIMES_CHANGED` of the open project reads the list again. A clean editor
    follows the change (and closes when the runtime was deleted); an editor with changes keeps
    them and says "changed elsewhere" or "deleted elsewhere". Its own writes are counted as echoes
    and the match is without case, since the event of a save carries the request id. An event of
    another project changes nothing. A viewer and an operator see the form read only, may Check,
    and get no Save, Delete, Add, Load, Run, Stop or Unload.
  - **The runtime card and Run, Stop, Unload.** A task card "Runtime" in the editor reads the
    `GET /api/v1/runtimes` poll while the editor is mounted. It says NOT LOADED only after a good
    read that lists no runtime of that id, the core's mode (with the reason, program and version)
    when the core lists it, UNKNOWN when the read failed and nothing was read before, and the
    mode with LAST KNOWN when it failed after. When the core lists `programs`, each program shows
    the version that runs beside the version of the last build made here, or else of the last ok
    check made here; "not known" when neither exists, "the same" or "another version" otherwise.
    The card shows no task figure. Run asks first and names the programs. Stop is offered whenever
    the core lists the runtime, even when the last read failed, and asks nothing. Unload asks,
    says that the outputs go to their safe values, and sends the core's configuration without that
    id and with every other instance as read. Run and Unload are disabled when the runtimes could
    not be read; none of the three is offered when the runtime is not listed.
  - **Build and Load, with the plan.** Load (its title says that it saves the draft first if it
    has changes) does these in order, and stops at the first refusal with the refuser's words,
    saving nothing: it saves the draft when it has changes; `POST /runtimes/<id>/check {}`,
    which stops the load when not ok; `POST /runtimes/<id>/build`; `GET` of the core's runtimes
    configuration. `planLoad` then
    keeps every saved instance except the one of this id, those in the build's `replaces`, and the
    holders: an instance whose program's `built_from` equals, without case, one of the new
    instance's. A holder that is a configured runtime (a fresh `GET /runtimes`; when that read
    fails the load stops with words naming the holders) is built again with `POST
    /runtimes/<holder>/build` and put into the same save in place of its old instance, so that the
    core's refusal of one program in two runtimes does not apply; a refused build stops the load,
    names that runtime and shows the module's words. A holder that is not configured is taken out
    whole. An instance with no `built_from` whose PROGRAM name equals one of the new instance's is
    kept and the question says it "may also run" the program (built before 0.8.0, not compared by
    the core). The order of the saved instances is the order read, then the new instance, then the
    rebuilt holders.
  - **The question before the save.** `window.confirm(loadQuestion(plan))` names the runtime and
    whether it starts cold; for each program the version it loads and the version the core says
    runs now ("not known" and why when the runtimes could not be read, "last known" when a read
    failed after one succeeded, "none: the controller runs no build of it" only after a good
    read); the ids taken out (`replaces`, holders not configured, with the programs each ran); each
    rebuilt runtime with its programs and "restarts warm" ("restarts cold" for Load cold); and the
    instances that "may also run" a program. Load cold asks `loadColdQuestion` first, before the
    draft is saved or anything is built, and then asks the plan question. Nothing is sent to the
    core's runtimes configuration before the engineer confirmed the plan question. A cancel sends
    no `PUT`.
  - **What the answer shows.** The answer of the core's `PUT` is shown as given. `applied: false`
    says "Saved into the project's runtimes. The controller runs another project, so nothing was
    started." and no start. The `changes.failed` entries of `runtime:<id>` of this runtime and of a
    rebuilt one are shown in the core's words, and only those: no start is claimed for a runtime
    that failed. For this runtime and each rebuilt one not in `failed`, the start the core
    reported (`describeStart`) is shown with `dropped`, `initialized` and `not_given` listed as
    variable and why. The build's `warnings` are shown verbatim, and so are `project_problems`.
    The result says "applied by the controller" and sends the engineer to the card to see whether
    the runtime runs; the word "loaded" is not used of a runtime in the result. A refused `PUT`
    shows the core's `error` and every `problems` entry as `connection_id: message`, verbatim.
  - **The program's Task panel.** In a program's inspector, a program that a configured runtime
    runs is assigned by the logic module's configuration read with the runtimes poll (the program
    name matches without case), not by the runtime state. The panel says "Runs in task <t> of
    runtime <id>", gives a button that opens the runtime editor, shows the task's kind, priority
    and watchdog as configured (from `describeKind`; a missing number says UNKNOWN), and shows no
    input for interval, module, target or run, which a runtime build ignores. A program in no
    runtime shows its own settings as before. While the configuration is not known yet, the own
    settings are shown with a line saying that it is not known. The program editor still shows
    such a program as UNKNOWN, now with a button `runtime-open` that opens the runtime editor
    beside the reason.
  - **`not_given` and the core's problems on a program's Load.** A warm start that withheld
    RETAIN values lists them in the program editor (`program-not-given`) and its text says "except
    those listed as not given" instead of saying that every RETAIN variable started from its kept
    value. A refused Load of a program shows the core's `problems` beside the error they belong
    to, verbatim.
  - **The HMI tag list.** `ui-shell/src/data/programTags.ts` lists the published tags of every
    program of an instance (`program` or `programs`), and the type in `ui-shell/src/api/client.ts`
    gains `programs`. Before, a runtime of several programs contributed no tag.
  - **Version.** `plugins/logic` and `@mythos/logic-ui` are 0.10.0, and the entry of
    `mythos-logic` in `Cargo.lock` follows (the only change to the lock file).

  **The rules that keep the screens truthful.**
  - A runtime is "configured" (the logic module's file), "loaded" (the core lists it, with the
    mode the core reports) or neither. No text words one as the other. The editor says "Runtime
    <id> as configured in the project's logic module. Whether the controller runs it is on the
    Runtime card, as the controller lists it."
  - A read that failed is said where the list or the form would be, and is never shown as an
    empty list: the tree's list, the module list, the project's programs, the other runtimes'
    holders, the core's runtimes.
  - What is shown as saved is what the module answered, not what was typed: the read after a save
    (or the PUT's own answer, said to be that), and the module's stored defaults (a cycle task
    saved without its shortest cycle shows 0).
  - No default stands in for a decision: a new runtime has no run choice, a new task has no kind
    and no priority, and a body with a missing decision is not sent.
  - No version is called the same without a build or a check made here to compare.
  - A task shows no state and no figure in this slice.
  - A refused request shows the refuser's words (the `error` of its body, and the core's
    `problems`), and changes nothing on screen that claims to be saved or loaded. When the
    workbench withholds the body of a refusal, the screen says WITHHELD for a save, a check and a
    read alike.
  - The UI re-implements no rule that the module or the core owns: the id rule, the task rules
    and the one-runtime rule come back in their words.
  - The ids in addresses go through `encodeURIComponent`.

  **Departures and decisions of the stages.**
  - Stage 1.
    - The types allow a draft's open decisions as null (run, a task's kind, a priority, a cyclic
      interval), because the fixed `bodyOf` and `isRuntimeDirty` apply to the draft. What the
      module stores always has them. `sentOf` builds the complete body and returns null while
      `missingOf` is not empty.
    - `missingOf` also names a cyclic task's missing interval, since the module's serde has no
      default for it. A phase, a shortest cycle and a watchdog that are empty are left out, so
      the module's default applies (the form says so). An empty event tag, task name, module or
      target is sent and the module answers in its own words.
    - The program list of "Add program" comes from the programs store; "in runtime <id>" comes
      from `GET /runtimes`. The module list is read once when an editor opens and is not polled.
      `profile.tasks.kinds` is read defensively in `runtimes.ts`, since the type of `bridge.ts`
      changed only in stage 2.
    - Check is not disabled while a check is in flight, so a newer draft can be checked and the
      older answer is dropped.
    - Echoes are D4c's mechanism (counted, deferred while a write is unanswered, then later); an
      echo is used up even when no editor is open.
    - A new runtime is listed in the tree apart until the module lists it, as in D4c.
    - The tree icon Cpu is already imported by `ProgramsTree`; the editor's icons are already
      imported by other files of the package; `logic.css` gets two layout rules and no value.
    - The harness's build route was modelled in stage 1 and called by nothing until stage 2.
    - When the read after a 200 save fails, the editor shows what the PUT answered, said to be
      that; D4c has no stored body in its PUT answer.
  - Stage 2.
    - The store's function is `loadRuntime(id, cold)`, not `load(id, cold)`, because
      `useRuntimes` already has `load(projectId)`. The fixed lines `if (!checked.ok) {` and
      `if (!window.confirm(loadQuestion(plan))) return false;` are in its steps, unchanged.
    - The contract's R18 asks that Load's title names the runtime editor. It is not done: a C8c
      test asserts that the program's Load title equals the UNKNOWN reason, and the five C8c tests
      must pass unchanged. The way to the runtime is the `runtime-open` button.
    - The card's commands have the test ids `runtime-card-run`, `runtime-card-stop` and
      `runtime-card-unload`, because `runtime-run` and `runtime-stop` are stage 1's run-choice
      radios in the same editor.
    - `planLoad` takes two parameters the contract does not name, the rebuilt holders' builds and
      the core's runtimes as last read, so that `loadQuestion(plan)` keeps its one argument and can
      say the version that runs per program.
    - Rebuilt runtimes are said to restart warm for Load and cold for Load cold, from the core's
      documentation of `?start=cold`. A rebuilt holder's own `replaces` are not removed.
    - Unload and the card match an instance id exactly, as the core's ids are matched.
    - The program editor's Task panel decides "assigned" from the configuration, not from the run
      state; the null `interval_ms` of a runtime with no cyclic task reads "none: it has no cyclic
      task".
    - Only the build's own warnings are shown for a retained data block (below).
  - The review fixes (below) changed the number fields: a field keeps the typed text and gives the
    draft what empty stands for (watchdog: the key is left out, phase and shortest cycle: 0,
    interval and priority: null), and shows a value that came from elsewhere as it is.

  **The two reviews and what was done.** The review of the editor (stage 1) returned nine
  findings, and all nine were fixed in one commit (`eadd78c`). The review of Load (stage 2) did
  not return: no finding of it exists, and Load, the card and the program side have had no
  second reading by an agent. The fixes themselves have had none either.
  - F1 (medium, LIVE). The echo of the editor's own save that arrived while a later save of the
    same runtime was out was deferred; the later save was refused, so the event was followed as
    somebody else's write (a false "changed elsewhere"), and the echo left unused swallowed the
    next real event. Fixed in `runtimestore.ts`: an outstanding echo of an earlier 200 write is
    counted before an event is deferred to an unanswered write. Test: the echo of an own save that
    comes while a later save is out, and the module's events before an answer.
  - F2 (medium, LIVE). A runtime with changes here that was deleted elsewhere vanished from the
    tree while its draft and the unsaved owner stayed, so the work could not be reopened. Fixed in
    `RuntimesTree.tsx`: every doc that is new or has changes and that the list does not hold is
    listed apart, with the label that says why. Test: "a runtime with changes here that was
    deleted elsewhere stays in the tree, marked unsaved".
