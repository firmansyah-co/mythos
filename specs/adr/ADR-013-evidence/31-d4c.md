# ADR-013 evidence: D4c

Part of [ADR-013](../ADR-013-logic-compiler-and-vm.md), section 5.

- **D4c** (the library editor in the logic module's workbench UI, the third part of ADR-014's D4,
  2026-11-23). A project's library of functions and function blocks can now be edited in the
  workbench, in the UI the logic module ships, and a program's check follows the library and the
  project's types. No route, no MCP tool and no Rust behaviour changed: the five library routes
  and their tools existed since D3, and the one Rust edit is a doc comment. Library blocks in the
  LD and FBD palette, and the live values of a data block, are not built.

  **What the slice adds.** All of it is in `frontend/packages/logic-ui`, version 0.9.0, with
  `plugins/logic` at 0.9.0 (the version agreement test requires a module and its UI to match).
  - **The tree section.** "Library" (id `logic-library`, order 25, between Programs 20 and Data
    30) is a node that lists what `GET /library` answered, in the module's order, each source with
    the mark ST. A source opens the editor kind `logic-library` (title "Library", the name) on a
    double-click or Enter. A failed list read shows the module's words (`tree-library-error`) and
    lists nothing. "No library sources yet." shows only after a 200 with `[]`, and "Reading the
    library..." before. An engineer gets the row "Add new source". A name that the list holds in
    any ASCII case opens the stored spelling. Any other name opens an editor marked NOT SAVED YET
    and writes nothing. The tree lists such a source as "<name> (not saved yet)" with the unsaved
    mark until the module lists that name or it is discarded.
  - **The editor.** It shows the stored text in the package's Structured Text `SourceEditor`
    (a library source is Structured Text only: the compiler's library is a list of ST texts, so
    the LD and FBD editors cannot serve it). A 404 shows the module's words and no editor. A 500
    on the read shows the module's words above an empty draft, and Save replaces the file and
    Delete removes it, since the routes mend such a file. The inspector's Diagnostics tab (owner
    `logic-library-check`) lists the last check: a diagnostic in this source is drawn on the text
    and is a button that places the caret; one in another listed library source is a button that
    opens that source at its line; one in a type's file, or with no source, is plain text with
    its place ("about the whole" at line 0); `project_problems` are listed apart.
  - **Check before save, and "Save anyway".** Save first sends `POST /library/check {name,
    source}` with the draft. A refusal (400 name rule, 409 other spelling) is shown in the
    module's words and nothing is saved. A check that is not ok holds the save: `save-held` says
    that with this text the library does not check, and Save anyway asks a confirm and then sends
    the `PUT`. A check that is ok sends the `PUT`, then `GET /library/<name>`, and the text shown
    as saved is the one read. `created: true` reads the list again.
  - **What an ok check claims.** "The library checks with this text, with the project's types and
    data blocks", and a footnote that programs are not checked here. The module's check compiles
    no program: a program that declares a name the library declares, or uses what the text no
    longer has, is refused at its own check. The screen never says that programs compile. When
    the module answers `ok: true` with `project_problems`, the text says the library was checked
    without all of the project's types and data blocks.
  - **Programs follow the library and the project's types.** On `LOGIC_LIBRARY_CHANGED` and on
    `DATA_CHANGED` of the open project, every program that has a check is marked as checked
    against an earlier library, earlier types, or both, and nothing of that check is drawn as
    current: not the badge COMPILES, not the diagnostics, not the live state of a diagram, not the
    variables of the Interface. The badge reads LIBRARY CHANGED SINCE CHECK, DATA CHANGED SINCE
    CHECK or LIBRARY AND DATA CHANGED SINCE CHECK. Each program whose source was read is then
    checked again quietly, and its answer clears the mark. A program never read is not checked.
  - **The link from a program's diagnostic.** A diagnostic of a program's check whose source is
    `logic/library/<N>.st`, with N in the last successful `GET /library`, is a button
    (`diagnostic-library`) that opens the library editor on N and puts the caret at its line and
    column (line 0 opens only). When N is not listed, or the list was not read, it stays plain
    text.
  - **The state of the whole library on the tree node.** After the list is read, and after each
    of the two events, the store sends `POST /library/check {}`. The Library node carries
    DOES NOT CHECK with the count of diagnostics the module answered, and the title "Every
    program of the project is refused while the library does not check.", or NOT CHECKED with the
    module's words in the title when that request failed. When the library checks, the node
    carries no mark: nothing is claimed about programs. Nothing shows while no answer is in, and
    an answer from before a change is not shown after it.
  - **The corrected LD and FBD words.** A box that the editor does not know was marked "X is not a
    function or function block this program can call", which was false since D3 (a program is
    compiled with the library). It now says that the editor knows this program's own blocks and
    the standard ones, and that if the project's library declares X, Check compiles the program
    with it. Only words changed: what the mark allows or blocks is as it was. The header comments
    of `ldcatalog.ts` and `fbdcatalog.ts` and the doc comment of `plugins/logic/src/lib.rs` (each
    program is compiled from its own source and the project's library) were corrected too.
  - **Version.** `plugins/logic` and `@mythos/logic-ui` are 0.9.0, and the entry of `mythos-logic`
    in `Cargo.lock` is the one changed line of that file. The words "since 0.8.0" in the module's
    tool summaries stay: they name when something began.

  **The rules that keep the screens truthful.**
  - A name appears only if `GET /library` answered it or the user typed it (and it is then marked
    NOT SAVED YET). A list that could not be read is said where the list would be, never shown as
    empty. No count of programs, no "used by" and no "programs compile" appears: the module
    answers none of those.
  - What is shown as saved is what the module answered. After a save the text is read again and
    shown, and if that read fails the editor says so and stays marked UNSAVED. A refused save
    shows `error` of the module's body and changes nothing that claims to be saved.
  - The UI has no name rule. The Add row only refuses an empty field. A name the module refuses
    (not a letter followed by letters, digits or `_`, over 64, a Windows device name, another
    spelling of a stored name) is shown in the module's words.
  - A check of an earlier text, earlier library or earlier types is badged as such and draws
    nothing on the text, and its count in the Diagnostics tab is null. A program's check from
    before a change is never drawn as current, and an answer asked before a change does not clear
    the mark for it.
  - A save sends only a text that was checked, or a text whose check held the save and that the
    engineer confirmed unchanged. A CRLF file opens clean (text is compared with CRLF read as LF).
    Names go in URLs through `encodeURIComponent`.
  - A viewer and an operator see the source read only and may Check. Without accounts anyone may
    edit, as in the rest of the logic UI.
  - Only the workbench's classes, components, icons and tokens are used (the tree icon is
    `FileCode2`); `logic.css` is unchanged.

  **Departures and decisions of the stages.**
  - The mutations were run in the slice worktree after each commit, each file restored with
    `git checkout --`, and not in a `git archive` copy, since a copy needs its own `node_modules`
    on a machine that is slow under load. The status was clean after each run.
  - The contract's mutation M10 (`if (library.projectId === null) return;`) does not typecheck
    under `noUnusedLocals`; `... || project === undefined` was used and goes red on the same
    test. Its M15 text occurs twice in `programs.ts`; the line before it was included to make it
    unique. M14 is adapted to `checkIsCurrent` with both flags.
  - The target `const back = await api.readSource(...)` reads that way because the package's api
    object is `libraryApi`, imported `as api` in the store. The re-check of the programs is in a
    local `changedUnder(cause)` that both `libraryChanged()` and `dataChanged()` call.
  - A refused check in Save is shown once, in `save-refused`; `check-refused` is for the Check
    button.
  - Discard on a new source drops it and closes its editor; on a stored source it returns the
    draft to the saved text (changed by the review where the source was changed elsewhere).
  - A 500 on the read is treated as the replaceable file. The UI cannot tell "not UTF-8" from
    another failure, and the module's words, with its server path, are shown as answered.
  - An own diagnostic at line 0 is plain text with "about the whole", since there is no place for
    the caret. The Diagnostics count is the number of diagnostics of the last check (0 when ok)
    and null before any check; `project_problems` are not counted.
  - A new source starts with an empty draft. What the module answers for an empty source is NOT
    VERIFIED, and no test assumes either answer.
  - Events of the editor's own write are matched as in D4a: one heard while the `PUT` is
    unanswered is decided by the answer; one heard after it is matched against a count; one heard
    during the check or the read-back is somebody else's and followed once the editor is idle.
  - After `DATA_CHANGED` the editor's own check is marked "(EARLIER TYPES)" (not returned to NOT
    CHECKED): neutral tone, nothing drawn, count null. A check asked before the event and answered
    after it is marked too.
  - While a program's check is stale for the library or the data, its Diagnostics show only the
    stale line, and the live state says why nothing is drawn. A changed text keeps the old
    behaviour (the old list under `check-stale`), and the badge says CHANGED SINCE CHECK even if
    the library also changed.
  - Every program check is now numbered per program, so an older answer never replaces a newer
    one, user checks included (before, a user check's answer was always applied).
  - `DATA_CHANGED` is filtered by its `project` only; its other fields are not read, so a shape
    the data module adds later still marks checks stale. The data module's event data is
    `{project, what, name, change}`.
  - The state of the library on the tree node is sent only after a list read that succeeded.
  - `other-sources.test.tsx` was not extended: its test of a library diagnostic passes unchanged
    (its backend has no library, so the source is not listed and stays plain), and the new tests
    are in `library-programs.test.tsx`.
  - The `act(...)` warnings React writes to stderr in some tests (older tests too) did not fail
    any test.

  **The two reviews and what was done.** One review took the library screens and one took the
  programs and the package. Each finding was reproduced by its reviewer before it was reported.
  - Screens, LIVE (high): Save anyway could send a text that was never checked, and `save-held`
    stayed on screen after the text changed or after a Check answered CHECKS. Fixed: `held` is
    the text whose check held the save; a change of the text, a check of the new text that is ok,
    or a change of the library or types drops it, and `save(name, true)` sends nothing unless it
    equals the draft. Save anyway is withdrawn, not re-checked: the reviewer's repro that
    expected a `PUT` of the edited text stays red by design. Tests named above.
  - Screens, LIVE: the editor's CHECKS stayed after another library source was saved or deleted.
    Fixed: "(EARLIER LIBRARY)" in neutral tone, count null, nothing drawn; the source the event
    names is exempt, since its check put the draft in the stored text's place.
  - Screens, LIVE: an ok check said it was made with the project's types and data blocks when the
    module had answered `project_problems`. Fixed, and the note now says what the module does:
    the data blocks are always left out in that case, and the types unless they check alone.
  - Screens, LIVE: Discard after a change elsewhere showed the old text, or an empty one for a
    source deleted elsewhere, as clean and unsaved-free. Fixed: a source changed elsewhere is
    read again; one deleted elsewhere is dropped and its editor closes.
  - Screens, LIVE: after a delete from the editor the editor read the source again and left a 404
    entry that blocked making a new source of that name for the session. Fixed: the doc is
    forgotten after the editor closes, and the editor does not read while it closes.
  - Screens, LIVE: a new source vanished from the tree when a name differing only in case was
    made elsewhere, and was told "saving replaces that change" before a 409. Fixed: it stays
    listed until the module lists its exact name, and the notice names the other spelling and
    promises nothing.
  - Screens, LIVE (low): text typed while a change elsewhere was being read was lost when that
    read failed. Fixed: a dirty draft is kept; 404 says deleted elsewhere, any other failure says
    changed elsewhere.
  - Screens, test only: the fake answered a name holding `/` with the module's name rule, which
    the core never forwards (it answers 404 `module 'logic' serves no ...`), and its words for a
    source that is not UTF-8 differed from the module's. Fixed in `harness.tsx`.
  - Programs, LIVE: the Interface panel kept listing the variables of a check made with earlier
    types or an earlier library, with Bind selects, and nothing said so. Fixed: the variables get
    a stale cause, `variables-stale` names it, and an ok check that gives variables clears it.
  - Programs, LIVE (low): the caret landed N-1 characters off in a library source with CRLF line
    ends, because offsets counted `\r` and a browser's textarea does not. Fixed in
    `SourceEditor.tsx`, which now shows the LF text; this also fixes the program editor's go-to,
    which had the same cause before this slice. Where the caret lands in a real browser is NOT
    VERIFIED.
  - Programs, LIVE (low): a go-to into a library editor with unsaved changes put the caret at the
    stored text's line and column counted in the draft, and said nothing. Fixed: the caret stays
    and `library-unplaced` says the place is of the stored text (or of the text that was checked).
  - Programs, LIVE (low): the Library node used a lucide icon no workbench package shipped.
    Fixed: it uses `FileCode2`. No DOM test pins an icon; the proof is that `git grep` of the
    lucide imports at `origin/dev` lists `FileCode2` and not `Library`.

    contract are NOT VERIFIED: the toolbar with Save anyway in a narrow work area, the tree with
    200 sources, a source of 2,000 lines in `SourceEditor` (it paints every token on each change),
    the badge of the library's state in a narrow tree, the stale line, the layout of the
    `diagnostic-library` button, and the caret in a CRLF source.
  - Nothing was run on Windows or macOS by the agents. CRLF is covered by tests on Linux, and the
    names go through `encodeURIComponent`.
  - The full `./scripts/check.sh` (Rust fmt, clippy, workspace tests) was not run by the stages.
    The Rust edit is a doc comment and the version line.
  - What the module answers for an empty library source is NOT VERIFIED: no test of the UI
    assumes either answer.
  - No test covers two events heard while one `PUT` is unanswered (one is held), nor an echo lost
    by the event stream (a count left over would swallow a later change); both were reasoned, not
    executed. An event missed while the stream reconnects leaves COMPILES standing: this holds for
    every event-driven mark and is not specific to this slice.
  - Whether the LD, FBD and SFC editors lose a selection or an undo history when their props
    change after a stale mark was not tested.
  - The injected text of each stage-2 mutation was not typechecked separately; each keeps every
    identifier it touches in use (read, not run).

  **What is left out of D4c.**
  - Library blocks in the LD and FBD palette, with their pins (LIVE gap, a later slice). The
    module does not answer a library block's interface, so the LD and FBD editors still offer
    none and cannot draw one; only the words of the mark changed. A box naming a library block is
    still marked in the editor and compiled by the module.
  - A save checks nothing in the module, so an MCP caller can save a broken library, which refuses
    every program (LATENT, by decision: a change across two sources needs a save that does not
    check, and a refusal would change a tool's contract).
  - No revision precondition on a save, so the last save wins; the event warns an editor with
    changes, and a check followed by a save can still cross another client's write (LATENT).
  - No answer naming the programs a library change breaks. A program shows it at its next check,
    and the workbench re-checks only the programs it has read.
  - A read error shows a server path: `GET /library` and `GET /library/<name>` answer the absolute
    path with the I/O error (LATENT, authenticated viewers only). A 500 is also both "not UTF-8"
    and any other failure, which the UI cannot tell apart.
  - A diagnostic in a type's file (`data/types/...`), from the library or a program, stays plain
    text; it does not open the data module's editor.
  - The live values of a data block (D4b, after C8d).
