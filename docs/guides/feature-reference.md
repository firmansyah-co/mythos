# Feature reference

Everything that runs today, piece by piece, with where it lives in the tree. This page is the detailed status of the project; the [README](../../README.md) has the summary. Anything under `docs/01-…` to `docs/04-…` and `specs/` is design intent and may describe things that do not exist.

## What runs

| Piece | Where | State |
| :--- | :--- | :--- |
| Tag bus | `crates/mythos-shm`, `crates/mythos-pal` | Triple-buffered shared-memory tag store with typed values and OPC-style quality codes. One writer: the field I/O runtime. |
| Modules | `crates/mythos-module` | Every driver is a separate executable, `mythos-module-<name>`, that the server finds beside itself (or in `MYTHOS_MODULE_PATH`), starts as a child process and talks to over JSON lines on its standard streams. Nothing is compiled into the server. A module process that dies is replaced; its tags read `BAD_COMM_FAILURE` until it is back. A new build of a module put in the directory is noticed within two to four seconds (a change is acted on once it has held still for one look, so a half-copied file is never started) and swapped in for the running one without its tags stopping; a new build that cannot start, or a module that goes missing, leaves the old one running. See [ADR-010](../../specs/adr/ADR-010-modules-are-processes.md). |
| Service modules | `crates/mythos-module/src/service.rs`, `crates/mythos-core/src/services.rs` | A module of kind `service` (ADR-011) declares its routes in its manifest, each with the least role it needs. The server mounts them under `/api/v1/projects/<id>/<module>/…` or `/api/v1/m/<module>/…`, refuses a caller without the role before the module sees the request, gives the module its own data directory per project (`<project>/<module>/`), relays the events it sends on the telemetry stream, and makes every declared route an MCP tool. Its process is started on first use, started again when it dies, and replaced by a new build without dropping requests. A route that must check against the tag catalog declares `needs: ["tags"]` and is given the registered tag URIs with each call. The HMI is one (`plugins/hmi`). |
| Node | `crates/mythos-core/src/node.rs`, Settings → Node | Every installation is a node (ADR-012): `<storage root>/.mythos-system/node.json` holds an id that never changes, a name, a site and a role — `workstation` (the desktop app: listens on this computer only), `edge` (`mythos-server`'s default: every interface) or `server`. `MYTHOS_ROLE` chooses the role on first start, `MYTHOS_BIND` overrides where the server listens. The network uses HTTPS with the node's own certificate (`--https-port`, `MYTHOS_HTTPS_PORT`, default 8443): a browser on another computer opens `https://<node>:8443` and accepts the certificate once, after comparing its fingerprint with the one Settings → Node shows. Plain HTTP (`--port`, default 8080) is answered on the node's own computer only, unless `http_on_network` is set. A server reads no field devices unless told to (`field_io`), and says so in the I/O status. `GET/PUT /api/v1/node`; a new role's listening address applies on the next start, and the page says so. `mythos service install [--role edge] [--port 8080] [--storage DIR] [--user] [--dry-run]` runs `mythos-server` at boot under systemd (Linux), launchd (macOS) or Task Scheduler as SYSTEM (Windows), restarted when it stops; `mythos service uninstall` removes it and keeps its storage; `mythos service status` asks the operating system. |
| Discovery | `plugins/discovery` (`mythos-module-discovery`) | An always-on service module (ADR-012 §2.2): announces this node over mDNS (`_mythos._tcp`, no Avahi or Bonjour needed) when its role or setting says so — an edge does — and lists the MythOS nodes it hears at `GET /api/v1/m/discovery/nodes`, shown in the Portal as "MythOS on this network". A node heard is a candidate: nothing connects to it or trusts it because it was heard. Nothing secret is announced. |
| Pairing | `crates/mythos-core/src/pairing.rs`, Settings → Pairing | Two nodes trust each other only once an administrator pairs them (ADR-012 §2.3): one makes a one-use pairing code (ten minutes, granting a role); the other gives that node's address, its certificate fingerprint (compared by a person) and the code, and reaches it over TLS pinned to that fingerprint, so a node presenting another certificate is refused before the code leaves. Each then acts on the other with the role it was granted (`mythos_pair_` tokens, stored only as hashes on the side that accepts them). Unpairing on either side reaches both. |
| Plant projects | `crates/mythos-core/src/plant.rs`, the Plant editor | One project engineers a plant of MythOS devices (ADR-012 §2.4): each device is a project of its own, assigned to this node or a paired one. Download sends a device's files to its node over the pairing; the node checks them, keeps what it ran, and runs the new ones, or runs the old ones again. Download all reports each device. Compare says whether a node runs exactly what the project says, and never says so when it cannot ask. A download needs `confirm: true`. |
| Tags across devices | `crates/mythos-core/src/remote.rs`, the Plant editor | A node running a plant reads the tags of its other devices over the pairing (ADR-012 §2.6, read only), named with the device: `edge1:external.Boiler.U1.p`, in the telemetry stream and `GET /api/v1/tags/values` like its own. While a link is down they are `BAD_COMM_FAILURE` with no value, never their last value. `GET /api/v1/remote` (MCP `list_remote_devices`) and the Plant editor say whether each link is live. |
| Fleet and call home | `crates/mythos-core/src/callhome.rs`, Settings → Fleet | Every paired node asked now: how it is reached, its version, what it runs (ADR-012 §2.6). A node the others cannot reach (another subnet, NAT, a workstation) is marked on its pairing to call home: it long-polls the node it pairs with over pinned HTTPS and is reached over that, for status, compare and download. A request given up on is never run late. |
| Settings → Modules | `crates/mythos-core/src/modules.rs`, the workbench | Every module found, with its state. An administrator can disable a module without deleting it (a disabled driver's connections stop with `CONFIG_ERROR` naming why; a disabled service answers 503), enable it again, install one from a package (a zip with `module.json`, a SHA-256 of every file and an executable per platform, built by `mythos module pack <dir>`), and remove an installed one. A package is refused unless every file matches its checksum, no entry lies outside its directory, it has an executable for this platform, and that executable answers `--manifest` with the package's manifest. Packages are installed into `<storage root>/.mythos-system/modules/`, which updates of MythOS leave alone. |
| Module UI | `frontend/packages/workbench-sdk`, `frontend/packages/ui-shell/src/modules` | A module may ship a workbench UI (`ui/entry.js`, ADR-011 §2.3). The server serves it at `/modules/<id>/ui/…` while the module is enabled; the workbench imports it after sign-in, and the module adds project-tree sections, editors, full-window views, inspector panels and task cards, each drawn with whatever the module bundles. The data module ships one (`frontend/packages/data-ui`), which the server serves from `modules-ui/org.mythos.data/`. A refusal that `host.api` throws carries the controller's status and body, so a module UI can show the reasons of a refused save. A UI that fails to load is named in the session log; the rest of the workbench works without it. |
| Writes to field devices | `crates/mythos-core/src/io/runtime.rs`, `PUT /api/v1/tags/<uri>/value` | An operator writes a number or a boolean to a tag whose driver declares it writable (`access_mode` `READ_WRITE`; for Modbus: a holding register of one register). The write runs in the connection's own task, between two poll cycles, with the poll's deadline. The answer says what is known: `written: true` when the device confirmed, `false` when nothing reached it (unknown tag, read-only tag, a value that does not fit), `"unknown"` when a request went out and no confirmation came back. A write never changes what a tag reads: the next poll does. Each write is logged with who made it. MCP tool `write_tag`. |
| Runtimes | `crates/mythos-core/src/runtimes.rs`, `plugins/runtime-vm` (`mythos-module-runtime-vm`), Settings → Runtimes | A project's `runtimes.json` says which control programs this node executes (ADR-013 §2.4). Each runs in a runtime module process: the VM runtime scans a program compiled to logic VM bytecode on its own clock. The server gives it the tags it reads, puts what it publishes on the tag bus as `internal.` tags, and writes its outputs to field devices. An output belongs to its program: an operator's write to it is refused, and a setpoint is a published variable marked writable. Whenever a program is not running (stopped, faulted, its process dead or silent, or unloaded) every output is written its safe value until the device confirms, and its tags are bad and say why. A program that dies is started again from a cold start. A runtime can run several programs in tasks (kinds cycle, cyclic, startup and event, each with a priority 0 to 31, 0 the highest); the VM preempts a lower task for a higher one, each task has its own process image and watchdog, and a variable of a runtime with several programs is named `<program>.<variable>`. The logic module stores a project's runtimes with their tasks and builds a runtime of several programs as one instance (the Logic module row below); the workbench edits and loads them (the Logic module row below) and shows no task state yet, and a runtime with several tasks reports no `scan_age_us`. RETAIN values are kept per runtime id and per program: a warm start gives a program only the values kept for it (the same project program when both name it, else the same PROGRAM name), a runtime of several programs gets them as `<program>.<variable>`, and what a load did not give is listed as `not_given`; a retain file written before is given once as it is and written again per program. An online change replaces a running program only with a build of the same programs of the same project, and another program starts warm. A project program is in one runtime: the core refuses a save in which two instances name the same one (`built_from`, given by the logic module's builds since 0.8.0; an instance built before is not compared). The programs of a runtime can share data blocks (ADR-014): each program has its own copy of a block, a member has one writer, and a block is handed over as a whole at the end of a task's run, with no exchange. Only the API and the MCP configure data blocks: the logic module's build of a runtime carries the union of its programs' blocks, once each, and the caller saves that instance. A program built before an update of the runtime module is still taken after it: the VM reads every bytecode format it extends (ADR-013 §2.3). `GET /api/v1/runtimes`, `POST /api/v1/runtimes/<id>/run` and `/stop`, `GET`/`PUT /api/v1/projects/<id>/runtimes`, each an MCP tool. The `GET` answers a `revision` (the lower hex SHA-256 of the stored file's bytes, of no bytes when there is none), and a `PUT` with `?revision=` of it is refused with 409, nothing saved, when the file has changed since the read; a `PUT` without it can overwrite a save made since the read, and a query key other than `start` and `revision` is refused with 400. `POST /api/v1/runtimes/<id>/watch` (any signed-in role; MCP `watch_runtime`) reads the values of a program's variables as its last scan left them, bound to a tag or not, one element of an array as `name[2]`, a STRING as its characters: all of one scan, with the program's state, how long ago it was read (`age_ms`, and `fresh_ms`, how old an answer may be and still be given at once) and how long before that its last scan completed (`state.scan_age_us`), and an error in place of a value for a variable the program does not have. Each list of variables is a watch of its own, so callers with other lists do not replace each other's; the runtime is read at each exchange for the union of every list watched of it (at most 256 names, at most 256 lists, a new list past either is refused with 409), and a list nobody asks for again within 5 s is let go. It changes nothing in the program. Settings → Runtimes in the workbench reads that list about once a second and shows, for every runtime, its module, program and version, its mode as reported with the reason given, its scan figures, and each output with its safe value and what the device last confirmed; an engineer runs and stops a program there (Run asks first: it is a cold start), and the page lists the runtime modules installed with the profile each declares. A value the server did not send is `UNKNOWN` or `NOT MEASURED`, and when a read fails or is not answered the rows are marked as the last known state with their age. Loading a program is not on the page: it is the API's. This is not a safety system: if the server itself stops, nothing writes anything. |
| Logic module | `plugins/logic` (`mythos-module-logic`), `frontend/packages/logic-ui` | Authoring of control programs, as a service module (ADR-013 §2.6) under `/api/v1/projects/<id>/logic/…`: a project's programs in Structured Text (`<project>/logic/programs/<name>.st`), Ladder Diagram, Function Block Diagram or Sequential Function Chart (PLCopen TC6 XML, `<name>.xml`; every graphical element keeps its id, so the live view draws each one's state; a chart's steps, transitions and actions keep theirs, so the chart's view draws each one's state, and so do the elements of its actions and conditions written in LD or FBD, for a view to come), each with its interval, its runtime and target, and its bindings of variables to tags (`<project>/logic/programs.json`). `check` compiles a program, or a text not yet saved, and answers with the compiler's diagnostics (line and column) or the program's variables and what its bindings get wrong. `build` compiles the saved source and packs it as a runtime instance; saving that instance into the project's runtimes (`PUT /api/v1/projects/<id>/runtimes`) is what loads it, so nothing that runs changes until then. A build's version is a hash of its code and bindings, and of the layout of the data blocks the program declares. The project has a library of functions and function blocks (`<project>/logic/library/<name>.st`; a source holding a `PROGRAM` or a `TYPE` is refused, and so is a name that is not a letter followed by letters, digits or `_` (at most 64 characters, and never a Windows device name: CON, PRN, AUX, NUL, COM0 to COM9, LPT0 to LPT9; names that differ only in case are one name); `GET`/`PUT`/`DELETE /library/<name>`, `GET /library` and `POST /library/check`, which answers each function and function block of a library that checks as `blocks`), compiled into every program, so a mistake in it refuses every program and names its file and line. A project can hold library packages (ADR-015 step 1): a package is a zip with `manifest.json` (format 1: id, version, `form` `source`, `languages` `st`, files, dependencies, licence), `checksums.json` and `src/<name>.st`; at most 1 048 576 bytes, 1024 entries and 2 097 152 bytes unpacked. `POST /packages` (engineer, the file as base64 in JSON, at most 1 398 104 characters) checks it and keeps it whole in `<project>/logic/packages/<id>/<version>.zip` (both names lower-cased, so ids that differ only in case are one), listed with its SHA-256 and origin in `<project>/logic/packages.json`; a name clash, a missing dependency, another stored package that does not read or an id already present in any case is refused, naming both places where there are two. `GET /packages`, `GET /packages/:package`, `POST /packages/check` (viewer; writes nothing) and `DELETE /packages/:package` (engineer; refused while another package that reads depends on it), each an MCP tool; a change sends `LOGIC_PACKAGES_CHANGED`. A stored package is read again at every read and compared with its recorded SHA-256; a file that is missing, changed or no longer reads is answered as a `problem` and not as a package. Programs are not compiled with packages yet: a package is kept and listed, and no program can call its blocks. No workbench UI yet. A program is built with the project's types and data blocks, which the logic module reads from `<project>/data/` and never writes: `VAR_EXTERNAL` names a block, `check` answers the blocks the program uses, and a build carries them in the instance's `data` and refuses what the runtimes would refuse for its data. When the stored data does not check, a program that declares no block still builds and every answer says why in `project_problems`. The module also stores the project's runtimes and their tasks in `<project>/logic/tasks.json`: a runtime has an id, a module, a target, `run` and a list of tasks (each a name, a kind of cycle, cyclic, startup or event, a priority and the programs it runs), and a program is in one runtime. A program no task names runs alone as before, in a runtime named like it; a project with no `tasks.json` builds and answers as it did. Nine rules refuse a runtime that is not well formed, one at a time, with their status and words (an id of 1 to 64 letters, digits, `-` or `_` that is not a Windows device name and not another runtime's or a program's name even in another case; a module; a target profile; at least one task; the protocol's task rules; only programs of the project; a program in one runtime). Six routes, each an MCP tool: `GET /runtimes` (`list_logic_runtimes`, with the runtimes that run alone as `implied` and the rules a hand-edited file breaks as `problems`), `GET /runtimes/:runtime` (`get_logic_runtime`), `PUT /runtimes/:runtime` (`save_logic_runtime`), `DELETE /runtimes/:runtime` (`delete_logic_runtime`), `POST /runtimes/:runtime/check` (`check_logic_runtime`, which takes a draft that is not saved) and `POST /runtimes/:runtime/build` (`build_logic_runtime`); in MCP the runtime is `runtime_id`. A build compiles each program for the runtime's target and answers one instance with its tasks and the union of its programs' data blocks, each program's version, `replaces` (the ids the programs run under alone, which the caller removes from the project's runtimes when it saves the instance), and warnings, among them that RETAIN values are kept per runtime id and per program and not given to another program. Every build names its project program (`built_from`) and its making (`created`) since 0.8.0. The module loads nothing. A program in a configured runtime is not built alone: its build is refused with 409 naming the runtime. Two programs that share a block are built into one runtime and loaded by saving the answered instance. A program moved from one configured runtime to another is refused by the core when the save holds it in both instances and both were built since 0.8.0 (take it out of the old one in the same save); an instance built before 0.8.0 is not compared, and its program runs in both until it is taken out. A runtime id reused for another program gives it none of the first program's kept RETAIN values on a warm load, except a retain file written before values were kept per program, which is given once as it is; RETAIN values do not follow a program to another runtime id. The logic module's writes hold a lock between processes. Every route is an MCP tool. Its workbench UI adds Programs, Runtimes and Library to the project tree, the runtime editor, the library editor and the program editor. The library editor shows a library source as Structured Text (the only language a library source can be written in) with the compiler's diagnostics, and checks the text with `POST /library/check` before it saves: a text that does not check is held, and an engineer can save it anyway after a confirm, since the module saves any text and a mistake in the library refuses every program. What is shown as saved is read again from the module, a list or source that could not be read is said and not shown as empty, a refusal shows the module's words, and an ok check says only that the library checks, since it compiles no program. A program's check is marked as of an earlier library, earlier types or both when the library or the project's types change, and the open programs are checked again; a program's diagnostic in a library source opens that source at its line; the Library node says DOES NOT CHECK, with the module's count, when the stored library does not check. A viewer and an operator get the library editor read only and may check. The LD and FBD palettes offer the library's functions and function blocks in a group "Library" and draw a box of one with the pins `POST /library/check` answered as `blocks` (only when the library checks; a list not answered is said with its reason, never shown empty); a box whose block changed or was deleted says so and its stored text is not rewritten. The program editor: Structured Text with the compiler's diagnostics marked at their line and column, the task settings, a table of the program's variables with their bindings to tags (an output has no safe value until one is given; a STRING cannot be bound, as a tag holds no text) and each bound tag's live value, what the controller's runtime of the program is doing, and each variable's value in the running program (a value read from a program that is not in RUN is marked as what it stopped with). A program that a configured runtime runs is UNKNOWN in the program editor, with the runtime named and a button that opens the runtime's editor, and its Load and the Runtime card's commands are disabled with that reason until C8d-2; its Task panel says which task of which runtime runs it and shows that task's kind, priority and watchdog as configured, with no input for what a runtime build ignores. Load of a program shows the core's `problems` when the core refuses the save, and lists the RETAIN values a warm start did not give (`not_given`). The Runtimes section of the project tree lists the configured runtimes (a program that runs alone is not listed; a list that could not be read is said, not shown empty) and opens the runtime editor: the module, target, run choice (no default) and the tasks, each with its kind, priority, watchdog and programs, checked with the module's draft check, saved (what is shown as saved is read again from the module), deleted after a question, and followed when another client changes it. A viewer and an operator see it read only and may check. Its Runtime card says NOT LOADED only after a good read of the core's runtimes that lists no runtime of that id, the core's mode when it lists a runtime of that id and the controller runs this project (when it runs another project, the card gives the runtime no mode), and UNKNOWN or LAST KNOWN when the read failed, with each program's version that runs beside the one last built or checked here; it shows no task figure. Load of a runtime saves a draft with changes, checks, builds, and then asks a question that names every program with the version it loads and the version that runs, the ids taken out, and each configured runtime that holds a moved program (rebuilt by the module, restarting warm) before it saves the core's configuration; an instance built before 0.8.0 that holds a program of the same name is named as "may also run" it and kept. The answer is shown as the core gave it, including what failed to start and the values not given. A runtime's Load and Unload and a program's Load and Unload send the revision they read, and a 409 is shown in the core's words; a runtime's Load against a core that gives no revision is refused before its question. Run and Unload ask first, Stop asks nothing and is offered whenever the core lists the runtime of this project. A Ladder Diagram is edited in a TIA Portal-like editor (instructions task card, favourites, networks) and drawn live with the power each rung kept; a Function Block Diagram is edited the same way, each network one tree of boxes laid out by the editor (an input takes one line; a second signal is joined with an OR), and drawn live with the value each line carried. A Sequential Function Chart is edited as S7-GRAPH's sequence editor works: a step and a transition put as a pair, alternative and simultaneous branches opened and closed at once, jumps and the end of a sequence, each refused with the reason where it would not leave a well-formed chart; a step's name, its action table (a qualifier of Table 59, its duration, and an action of the POU, a BOOL variable declared where it is named, or ST statements) and a transition's condition (an ST expression or a transition of the POU) edited where they are selected; every localId kept and none given to another element; a chart another tool wrote that the editor cannot draw, and every action or condition written in LD or FBD, kept as found; the editor says when a change of the steps restarts the chart at the next Load. A viewer and an operator get the three diagrams read only. A Sequential Function Chart is drawn, in the editor as in the view, with IEC 61131-3's symbols: steps (the initial one double-framed), transitions with their conditions, selection and simultaneous divergences and convergences, jumps, action blocks with each action's qualifier, and each diagnostic at its element; live, each active step is marked with its time, a transition's condition is TRUE or FALSE only where it was evaluated in the last scan ("not evaluated" otherwise), and each action's state is shown, UNKNOWN where a value cannot be read; an action or a condition written in LD or FBD, or as a network drawn in the chart, is named with its language and not drawn yet. Its TC6 document stays reachable as text, read only. Compile results go to the inspector's Diagnostics tab, the Runtime task card holds Run, Stop, Unload and Release all, and forcing a variable is an engineer's and is marked FORCED everywhere it shows. Load saves, checks and builds the program and puts it into the project's runtimes; Run, Stop and Unload act on the runtime. When the runtimes cannot be read the editor says UNKNOWN, or marks what it last read as last known. Watched values that are not current are drawn UNKNOWN in every diagram and in the variables table, with why, never as the program's: a read older than the route's `fresh_ms` and one interval of asking, or, in RUN, a program whose last scan had completed more than two of its intervals and its longest scan before the read (a scan thread stopped or behind, before the watchdog fires), or an answer that does not say how old it is; a read is aged from when it was asked, on a monotonic clock, against the interval of the version that answered, and an older answer coming back after a newer one is dropped (ADR-013 §2.8). A runtimes read unanswered for 3 s marks the Runtime card LAST KNOWN. |
| Data module | `plugins/data` (`mythos-module-data`) | A project's user types and data blocks (ADR-014), as a service module under `/api/v1/projects/<id>/data/…`, with its data in `<project>/data/`: a type is one Structured Text `TYPE` in `types/<Name>.st`, and the data blocks are `blocks.json` (each a name, a type and `retain`). Every write is checked with the compiler over the whole new state and is refused, and writes nothing, if that leaves the project's types and blocks not checking. A type name is a letter or `_` then letters, digits and single underscores, at most 64, and is never a Windows device name (CON, PRN, AUX, NUL, COM0 to COM9, LPT0 to LPT9); names that differ only in case are one name. Eight routes, each an MCP tool: list, get, save and delete a type, list, save and delete a data block, and check, which checks the stored state or a draft type without saving it. An answer gives each block's layout hash, size and members, and a save says which blocks changed their layout, so a caller sees which programs are out of date; a block of a state that does not check has no layout. A change sends `DATA_CHANGED`. Nothing is built or loaded by it, and the logic module builds programs with what it stores. Reading needs the viewer role and writing the engineer role. Its workbench UI, `frontend/packages/data-ui`, adds Data to the project tree with User types and Data blocks: a user type is edited as Structured Text, checked as a draft, saved and deleted, and a data block is edited as a type and an explicit choice of retain. Each editor shows what the module answered: a layout, size or member list the module did not give reads NOT KNOWN with the module's reasons, a list that could not be read is said and not shown as empty, and a refused save shows the module's words and diagnostics. After a type save the stored text is read again and shown. A block is compared with the blocks the open project's runtimes configuration carries and the row says at most "laid out as saved", since an initial value is outside the layout hash; the configuration is "configured", and whether it runs is not shown. A viewer and an operator get the editors read only. Not in the editors: rename, reorder, per-block initial values, nested members, where a block is declared, live values of a block, and a revision check, so the last save wins. Not checked in a real browser. |
| Field I/O runtime | `crates/mythos-core/src/io` | Each connection is a unit of its own: saving a configuration changes only the connections that differ, and one whose tags stay the same is swapped to its new settings without its tags stopping. Polls each configured connection and writes what the driver reports to the tag bus: a typed value with `GOOD` quality, or the last value read with a bad quality that names the fault. A tag that was never read has no value. |
| HMI module | `plugins/hmi` (`mythos-module-hmi`), `frontend/packages/hmi-ui` | HMI screens (drafts, release, sub-screens) and faceplate types and instances, as a service module (ADR-011 step 4) at the URLs they always had, `/api/v1/projects/<id>/hmi/…`, with its data in `<project>/hmi/`. A project whose screens and faceplates were saved by an earlier version keeps them: the module copies them in the first time it serves the project and leaves the originals. Its workbench UI is the screen editor, its toolbox and element properties, the project tree's HMI screens, and the operator runtime (`#/runtime/<project>`). Disabled, the workbench has no HMI and the routes answer 503. |
| API server | `crates/mythos-core` (`mythos-server`) | HTTP API for projects, data types and each project's I/O configuration, and the routes of service modules; a 100 ms SSE telemetry stream of the tag bus; `GET /api/v1/io/status` for the state of each connection. |
| Web workbench | `frontend/packages/ui-shell` | Portal view (open or create a project) and project view: project tree, devices & networks, a connection editor whose driver form is drawn from the driver module's JSON Schema (a new driver module brings its own form; a configuration without a drawable schema is shown and saved back as stored), live tag tables, connection diagnostics, inspector, Settings, and whatever the modules' UIs add (the HMI module: HMI screens with text fields and I/O fields bound to tags, saved as a draft and released, and an operator runtime that shows the released screens full window and follows a new release without a reload; the data module: editors for user types and data blocks). |
| Modbus TCP driver | `plugins/drivers/driver-modbus` (module `mythos-module-modbus`) | Reads holding and input registers as `u16`, `i16`, `u32`, `i32` or `f32`, with scaling and selectable word order. Exercised end to end against a simulated device, not yet against hardware. |
| MCP endpoint | `crates/mythos-core/src/mcp.rs` | `POST /mcp`, the Model Context Protocol over Streamable HTTP. Every API route is a tool (65 of the core's own, and each route a service module declares), or is listed with the reason it is not (the telemetry stream, static files); a test reads the router and fails on a route that is neither. A tool sends its route's own request through the same router. Checked with the official MCP TypeScript SDK client. |
| Platforms | `crates/mythos-pal`, CI | Linux, macOS and Windows. CI builds every Rust crate and runs the whole Rust test suite on each, the module and tag bus tests included. The tag bus is POSIX shared memory on Linux and macOS and a paging-file mapping on Windows. Real-time thread priority and core pinning exist on Linux and Windows; on macOS they report that they are not implemented. |
| Accounts | `crates/mythos-core/src/auth`, Settings in the workbench | Every route requires an account with enough of a role: viewer (reads), operator (also writes values to field devices), engineer (changes projects), admin (manages accounts). The workbench signs in with a session cookie; programs and MCP agents use personal access tokens. A new controller prints a one-time setup code in its log for creating the first administrator. Passwords are Argon2id hashes; sessions live in memory, so a restart signs everyone out. |
| Device catalog | `catalog/`, `crates/mythos-core/src/catalog` | Manifest format and parser, with two reference device packages. |
| Desktop shell | `src-tauri` | A Tauri window that embeds the same API server. |

## What does not exist yet

- **Any driver other than Modbus TCP.** A Modbus RTU configuration is rejected; there is no
  MQTT driver.
- **Screen elements beyond a text field and an I/O field.** No faceplates, graphics, trends or
  alarm displays.
- **Library blocks in the LD and FBD palette: what is left.** No front end supports VAR_IN_OUT
  pins, so none is offered; no action takes a changed declaration's pins; a favourite of a block
  not offered now disappears without a word; the source file of a block is not named.
- **Editors for faceplate types, data types and networks in the workbench.** The server still
  stores faceplate types and data types; the workbench has no editors for them.
- **Drawing and editing a chart's LD and FBD bodies, and a CFC mode for FBD.** SFC programs are
  edited, checked, built, loaded, run and drawn live (steps, transitions, every action qualifier of Table 59: N,
  R, S, L, D, P, SD, DS, SL, P1, P0; actions and conditions in ST, LD or FBD, a condition also as a network
  drawn in the chart), and the compiler keeps every value of an action's or a condition's LD or
  FBD network for monitoring, but the workbench neither draws nor edits those LD and FBD networks
  (the chart names their language and the editor keeps them as found), nor edits the POU's own
  actions and transitions (shown with their text);
  SD and SL run their full delay and limit from when the action was stored, their step left or
  not, and P0 pulses only in the scan after its step was left, never at a start (what Table 59
  names; where the standard's own block diagram does otherwise is in ADR-013 §2.17). Where two
  steps store one action, or a step is entered again with no R between, the action is off in
  doubt: SD starts only when every delay is over, SL ends at the first limit that is over. An
  action that is itself a chart or is written in IL is refused. The FBD editor lays each network out itself (standard FBD): free placement,
  an explicit execution order and lines drawn back are a later CFC mode.
- **Task configuration in the workbench.** A runtime runs several programs in tasks with
  priorities (the Runtimes row above). The logic module stores a project's runtimes and their
  tasks and builds a runtime of several programs (the Logic module row above), over the API and
  MCP. The workbench edits and loads a configured runtime and its tasks (C8d-1), but shows no
  task's state and cannot watch or force a program of a configured runtime (C8d-2); Settings →
  Runtimes shows no tasks.
- **Writes to field devices from the HMI.** The API has one (`PUT /api/v1/tags/<uri>/value`,
  see the table above); no screen element writes yet.
- **Alarms, historian, recipes, discovery of field devices, disaster recovery.** (MythOS nodes
  find each other over mDNS; field devices are not discovered.)
- **A device catalog for every protocol.** `crates/mythos-core/src/catalog` parses Modbus RTU
  device manifests only, and nothing uses it yet.
- **A published release.** Nothing has been published yet, so `mythos update` has nothing to
  install and says so. The one-line installers (`scripts/install.sh`, `scripts/install.ps1`)
  still name download hosts that do not exist.
